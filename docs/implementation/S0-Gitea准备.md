## 4. 启用 HTTPS，轮换凭据（ADR-0032 D0）

明文 HTTP 下，账号密码、访问令牌、执行机注册令牌、镜像推送凭据都会在公网上明文传输；Docker 也默认拒绝非 HTTPS 的镜像仓库。

| # | 操作 | 确认 |
|---|---|---|
| 4.1 | 选定域名（如 `git.<公司已备案的域名>`），在阿里云云解析添加 A 记录指向 Gitea 的公网 IP | `nslookup` 返回该 IP |
| 4.2 | 选择证书方式（二选一）：**A Gitea 内置自动证书（ACME）**：配置最少、证书自动续期，要求 80、443 端口对外可访问；**B 阿里云 SSL 证书 + 主机上的 Nginx**：证书由阿里云管理，Gitea 只监听本机端口 | 记录选择 |
| 4.3 | 选 A 时，在 `app.ini` 的 `[server]` 节设置：`PROTOCOL = https`、`DOMAIN = <域名>`、`ROOT_URL = https://<域名>/`、`HTTP_PORT = 443`、`ENABLE_ACME = true`、`ACME_ACCEPTTOS = true`、`ACME_EMAIL = <管理员邮箱>`、`REDIRECT_OTHER_PORT = true`、`PORT_TO_REDIRECT = 80`（HTTP 自动跳转到 HTTPS）。选 B 时，`ROOT_URL` 同样改为 `https://<域名>/`，由 Nginx 终止 TLS 并转发到 Gitea | 浏览器访问 `https://<域名>` 显示有效证书；访问 `http://` 自动跳转 |
| 4.4 | 阿里云安全组：只放行 443（选 A 时再放行 80 用于证书签发与跳转）以及 SSH（如使用 Git SSH 访问）；**关闭原来的 3050 端口** | 外网访问 3050 失败 |
| 4.5 | **轮换凭据**：所有曾在明文 HTTP 下使用过的个人访问令牌一律作废重建；所有账号修改密码；已有的 Webhook 与部署密钥一并检查 | 旧令牌访问 API 返回 401 |
| 4.6 | 本地开发机把旧仓库的远程地址改为 HTTPS（`git remote set-url origin https://<域名>/...`） | `git fetch` 正常 |

## 6. 部署执行机（ADR-0032 D2）

两类执行机部署在**两台独立的 ECS** 上，都不能与 Gitea 同机。

| 项 | `build` 执行机 | `release` 执行机 |
|---|---|---|
| 规格（初定） | 4 核 16 GB，系统盘 100 GB 以上（Docker 镜像缓存） | 2 核 4 GB |
| 运行的作业 | 格式、编译、测试（含 Testcontainers 启动 PostgreSQL）、OpenAPI 检查、依赖漏洞检查、构建镜像、镜像扫描 | 推送镜像、部署 |
| 持有的凭据 | **无**推送、无部署凭据 | 推送令牌、按环境分开的部署凭据 |
| 网络（安全组出站） | 只放行包源（nuget.org、npm 源）、镜像源、漏洞库下载地址与 Gitea；不能访问生产网络 | 可访问 Gitea 镜像仓库与部署主机 |
| 运行方式 | 官方 Docker 镜像 `gitea/runner:5.4.0-dind`，以 `--privileged` 运行：作业使用镜像内自带的 Docker，拿不到宿主机的 Docker 权限（Gitea Runner 官方推荐） | **S0-06 确定后补充**（见 6.5） |
| 标签 | `build:docker://docker.gitea.com/runner-images:ubuntu-latest`：名称为 `build`，作业在该镜像的容器中运行（S0-06 改为按摘要引用） | S0-06 确定后补充 |

| # | 操作 | 确认 |
|---|---|---|
| 6.1 | 两台 ECS 安装 Docker Engine | `docker info` 正常 |
| 6.2 | 拉取 6 表中的镜像，用 `docker image inspect --format '{{index .RepoDigests 0}}'` 记录**摘要**；之后启动容器时按摘要引用（ADR-0032 规则 1） | 记录到第 9 节 |
| 6.3 | 在 Gitea 中获取注册令牌：**限定到组织 `Krohne`**（组织设置 → Actions → 执行机），不用站点级令牌 | — |
| 6.4 | `build` 执行机：`docker run -d --restart always --privileged --name kmic-build-runner -e GITEA_INSTANCE_URL=https://<域名> -e GITEA_RUNNER_REGISTRATION_TOKEN=<令牌> -e GITEA_RUNNER_LABELS='build:docker://docker.gitea.com/runner-images:ubuntu-latest' -v /opt/gitea-runner/data:/data -v gitea-runner-docker:/var/lib/docker gitea/runner@<摘要>` | 组织的执行机列表中出现，状态“空闲”，标签 `build` |
| 6.5 | `release` 执行机：**先只准备 ECS 与 Docker，暂不注册**。它的作业怎么运行在 S0-06 设计流水线时确定，届时补充本步骤：候选做法一是同样用 `-dind` 镜像（需要 `--privileged`，但只运行受保护分支上的可信作业）；做法二是用不需要 Docker 的工具推送镜像（如从构建产物直接推送），执行机以 host 模式运行、不开特权。注意：不要把宿主机的 `/var/run/docker.sock` 挂给执行机，那等于把宿主机 root 权限交给作业（Gitea Runner 官方说明） | ECS 与 Docker 就绪 |
| 6.6 | `build` 注册完成后，在 Gitea 中让注册令牌失效（重新生成一个即可使旧令牌作废）；命令历史中的令牌一并清除 | 旧令牌不能再注册 |
| 6.7 | 并发等其他设置写在执行机的配置文件中（新版已不再支持 `GITEA_RUNNER_CAPACITY` 之类的环境变量）：`build` 先设 1 个并发，按实际耗时再调 | — |
