## 2. 日志

### 2.1 输出

| 环境 | 输出 |
|---|---|
| 开发 | 控制台（可读格式）+ OTLP 到 Aspire 仪表盘 |
| 测试、生产 | 标准输出 JSON（Serilog `CompactJsonFormatter` 风格）+ OTLP（配置了 `OTEL_EXPORTER_OTLP_ENDPOINT` 时）；不写本地文件 |

- 业务代码只用 `ILogger<T>`；Serilog 只出现在 `ServiceDefaults` / `BuildingBlocks.Infrastructure`（03 选型原则 5）。
- 默认级别：`Information`；`Microsoft.*`、`System.*` 为 `Warning`；`Microsoft.EntityFrameworkCore.Database.Command` 为 `Warning`（SQL 由第 3、4 节的追踪与慢查询日志覆盖）。级别可在运行中调整（05-10 D1 的唯一例外）。

### 2.2 富化字段

每条日志自动带上（由框架的富化器从执行上下文取得，业务代码不传）：

| 字段 | 来源 |
|---|---|
| `TraceId`、`SpanId` | 当前 `Activity` |
| `Origin` | `Http` / `Inbox` / `ScheduledJob` / `BackgroundJob` / `Startup` / `ModuleCall`（05-02 第 7.2 节） |
| `UserId`、`RoleId`、`ActualUserId` | `ICurrentUser`；系统身份为空，`IsSystem = true` |
| `Module`、`Message` | 当前处理的模块与消息名（中介者管道） |
| `MessageId` / `JobId` / `JobName` | 后台入口各自的标识 |
| `Service`、`Instance`、`Roles`、`Version` | 资源属性（OTel Resource） |
| `ClientIp` | HTTP 来源 |

- 只记录 ID，不记录姓名、手机号等（姓名在需要时由观测平台外的系统查询）。

### 2.3 D2 敏感数据如何脱敏

ADR-0016：敏感字段自动脱敏，不记录完整请求体和 SQL 参数。05-09 第 3.3 节已为审计定义了遮盖 / 隐藏 / 排除三级，日志要与之共用一套分类。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 在输出前用正则扫描整条日志 | 匹配手机号、邮箱、令牌形态的字符串替换掉 | 不需要标注 | 误伤（订单号像手机号）与漏网（格式不规则的密钥）并存；每条日志都要扫描，开销大 |
| **B 数据分类 + 官方脱敏库 + 禁止整对象输出** | 框架定义数据分类（`KmicData.Secret` / `Personal` / `Internal`）；日志使用源码生成的日志方法（`[LoggerMessage]`），参数或 `[LogProperties]` 中的属性按分类由 `Microsoft.Extensions.Compliance.Redaction` 脱敏；禁止 `{@obj}` 方式把整个对象写进日志（分析器）；属性名兜底规则（`Password`、`Token`、`Secret`、`Authorization` 等）由 Serilog 输出前处理 | 脱敏规则来自类型声明，确定、可测试；与审计共用同一套分类（审计映射中的 `.AuditMasked(...)` 改为引用同一分类）；性能好 | 需要在 DTO / 参数上标注分类；开发者要用源码生成的日志方法而不是随手 `LogInformation` 带对象 |
| C 只靠“不记录内容”的约定 | 05-02 已规定不记录消息内容 | 简单 | 异常消息、外部接口返回体中仍可能带出敏感数据，无兜底 |

- **决定（已确认，2026-11-04）**：B。分类与脱敏方式：

| 分类 | 例子 | 日志中 | 审计中（05-09） |
|---|---|---|---|
| `Secret` | 密码、令牌、密钥、验证码 | `***` | 只记“已修改” |
| `Personal` | 手机号、邮箱、证件号、地址 | 部分遮盖（`138****1234`） | 部分遮盖 |
| `Internal` | 内部 ID、业务编号 | 原样 | 原样 |

- 异常消息：框架的异常转换与未处理异常日志会把异常对象写入日志（含堆栈），**不**写入异常中附带的 `Data` 字典；`DbUpdateException` 等可能含参数值的异常由框架改写为不含参数的摘要（Npgsql 的 `IncludeErrorDetail` 在生产关闭）。
- **理由**：脱敏的可靠性来自“数据是什么”的声明，而不是对文本的猜测；同一个手机号在审计、日志中的处理规则一致。
- **取舍**：需要标注；高频日志必须写成源码生成的方法（这本身也是 ADR-0016 的要求）。
- 所有日志（测试项目除外）一律使用 `[LoggerMessage]`，CA1848 为 Error，不区分是否高频（06 D6）。

### 2.4 写法与级别约定

| 级别 | 用于 | 不用于 |
|---|---|---|
| `Error` | 未处理异常、死信、作业失败、需要人处理的问题 | 业务失败（`Result` 失败，如校验不通过、无权限） |
| `Warning` | 可自愈的异常情况：重试、缓存失效失败、慢查询、降级 | 用户输入错误 |
| `Information` | 请求摘要（D5）、后台处理开始 / 结束、启动任务、配置变化 | 循环内的逐条记录 |
| `Debug` | 开发诊断 | 生产默认关闭 |

- **预期异常不记 Error**（对应旧系统错误邮件的“白名单”）：客户端断开（`OperationCanceledException` 且请求已中止）、`BadHttpRequestException`、请求体过大，记 `Information` 或不记；由框架统一判断，不再维护关键词白名单。
- 消息模板固定、参数化：`"Sample {SampleId} submitted"`，禁止字符串拼接与插值（分析器 CA2254）。
- 一个错误只在最外层记录一次（异常转换行为或未处理异常中间件），中间层不 `catch` 后记录再抛出。

### 2.5 D5 请求日志的粒度

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 每个请求一条摘要日志** | 请求结束时记录：方法、路由模板（不含查询串）、状态码、耗时、`UserId`、`TraceId`、错误码；健康检查与静态资源不记 | 可按人、按接口检索“某人何时调用了什么”，用户报障时能快速定位；量可控（内部系统） | 日志量与请求量成正比 |
| B 只记录错误与慢请求 | 状态码 ≥ 500 或耗时超阈值才记 | 日志量小 | 4xx 问题与正常调用的上下文缺失，排查“用户说点了没反应”时无从查起 |

- **决定（已确认，2026-11-04）**：A。使用 ASP.NET Core 的 HTTP 日志（只启用请求行、状态码、耗时字段）或 Serilog 请求日志二选一，由框架实现，不记录请求头（除 `User-Agent` 截断）、请求体、响应体。
- **取舍**：日志存储随请求量增长；保留期由观测平台决定。
- **前端错误接收端点**（前端 F03 D9）：`POST /api/v1/operations/client-errors`（Operations 模块）。需登录（`[AllowAuthenticated]`），`[NotAudited("前端错误日志")]`；按用户限流，超限返回 429，前端丢弃不重试；请求为批量；字段白名单：错误类型、消息、堆栈（生产为压缩后的位置）、路由名、前端版本、关联的 `traceId`、发生时间，未知字段拒绝，各字段有长度上限（每次请求最多 20 条；错误类型 ≤ 100 字、消息 ≤ 1000 字、堆栈 ≤ 8000 字、路由名 ≤ 200 字、前端版本 ≤ 50 字；每用户每分钟 30 次，超限 429；数值见 `docs/modules/operations/README.md` 第 8 节，与前端联调时再核对）；不接收请求体、表单值、地址查询参数。后端用 `[LoggerMessage]` 写 `Warning` 级结构化日志，日志分类 `Kmic.ClientErrors`，消息与堆栈按第 2.3 节的属性名兜底规则处理后输出，与后端日志进入同一观测平台。source map 不随镜像发布，保存为 CI 制品。前端侧的去重与限量见 F03 第 15 节。

## 3. 追踪

### 3.1 覆盖范围

| 环节 | 来源 | 说明 |
|---|---|---|
| HTTP 入站 | ASP.NET Core 内置 | 路由模板作为名称 |
| 中介者管道 | 框架 `ActivitySource("Kmic.Mediator")` | 每个消息一个 span：消息名、模块、结果、错误码 |
| 数据库 | Npgsql OpenTelemetry | 记录 SQL 文本（参数化语句，不含参数值）；生产可配置只记录语句类型 |
| 缓存 | 框架 | `GetOrCreate` 的命中 / 未命中作为 span 事件，不单独成 span |
| Outbox → Inbox | 框架 `ActivitySource("Kmic.Messaging")` | 发布时保存 `traceparent`，投递与处理以**链接**关联原请求（ADR-0028 第 6 条），各自是新的追踪 |
| 定时任务、后台作业 | 框架 | 每次执行一个根 span；作业的每批一个子 span |
| 外部 HTTP | HttpClient 内置 | 对第三方是否传播 `traceparent` 按客户端配置（05-11 第 9.1 节） |
| 邮件、短信投递 | 框架 | 投递 span 链接到发送请求的消息 |

- 用户报障：前端在错误提示中显示 `traceId`（05-06 的 `X-Trace-Id` 与 ProblemDetails `traceId`），运维据此在观测平台找到整条链路；异步部分通过链接跳转。

### 3.2 D3 采样在哪里做

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 应用按比例采样（如 10%） | `TraceIdRatioBasedSampler` | 数据量小 | 报障时给出的 `traceId` 很可能恰好没被采样；错误和慢请求也会被丢掉 |
| **B 应用全量记录，采样交给 Collector（尾部采样）** | 应用使用 `ParentBased(AlwaysOn)`；Collector 配置尾部采样：错误、慢请求、带特定属性的全部保留，其余按比例 | 错误与慢请求一定保留；策略调整不需要发版；本系统请求量下全量导出的开销可接受 | 依赖 Collector 的配置（ADR-0016 已规划由 Collector 统一接收）；没有 Collector 时全量写入存储 |

- **决定（已确认，2026-11-04）**：B。在观测平台确定前，开发和测试环境全量保留。
- **理由**：追踪最主要的用途是“查某一个出问题的请求”，只有尾部采样能保证这些请求一定在。
- **取舍**：应用到 Collector 的数据量是全量；Collector 成为必需组件。

### 3.3 慢查询日志

- 框架的 EF 命令拦截器（05-03 第 7.4 节所指）：单条 SQL 超过 500 ms（配置项）记 `Warning`，内容为参数化 SQL 文本（截断 4 KB）、耗时、`Module`、`Message`、`TraceId`；不记录参数值。
- 数据库侧建议开启 `pg_stat_statements`，配合 `application_name`（`kmic-api` / `kmic-worker`，05-08 D2）区分来源，写入运维手册。

## 5. 告警

### 5.1 D1 告警由谁发出

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 应用自己发（旧系统做法） | 异常时应用发邮件，应用内去重、白名单 | 不依赖外部平台 | 数据库或邮件服务故障时恰好发不出来；进程挂了就没有告警；去重、静默、升级、值班都要自己实现；多实例下去重要共享状态 |
| **B 应用只输出日志与指标，告警由观测平台的规则发出** | 应用侧只保证信号完整（第 2～4 节）；告警规则、去重、静默、通知渠道在平台中配置 | 应用故障本身也能被发现（指标中断、健康检查失败）；成熟的去重与静默；规则修改不需要发版 | 依赖观测平台（ADR-0016 待决）；平台上线前没有告警 |

- **决定（已确认，2026-11-04）**：B。这一原则与具体选哪个平台无关；生产观测平台已定为自建 Grafana 栈（09 D6），测试环境用 Aspire 仪表盘人工查看。框架以文件形式维护建议的告警规则清单（5.2），实施时转为平台的规则格式。
- **理由**：FR-OBS-06 的 02 说明已给出原因——告警是平台的成熟能力，应用自发告警在最需要它的时候最不可靠。
- **取舍**：上线时观测平台必须到位，否则没有告警；这一点写入 08 实施计划的上线前置条件。

### 5.2 建议的告警规则

| 规则 | 条件（阈值均 `待确认`） | 级别 |
|---|---|---|
| 服务不可用 | 就绪检查连续失败 1 分钟；或 2 分钟内无任何指标上报 | 紧急 |
| 5xx 比例 | 5 分钟内 > 1% | 高 |
| 未处理异常 | `Error` 日志中 `Origin = Http` 的未处理异常出现 | 中（同一异常类型 + 位置 1 小时内只通知一次，对应旧系统的去重） |
| 消息积压 | Outbox / Inbox 最老消息 > 5 分钟，不含待终结订阅（05-07 第 9.3 节；同时用于发现“没有实例跑 Worker”，ADR-0025） | 高 |
| 死信 | `inbox.dead` > 0 或有序订阅阻塞键 > 0 | 中 |
| 定时任务 | 连续 2 次失败；出现 `Abandoned`；超过 2 个周期未成功 | 中 |
| 后台作业排队 | 最老排队 > 10 分钟 | 中 |
| 安全 | `AccountLocked` 同一 IP 10 分钟内 ≥ 3 个账号；`RefreshTokenReused`；`security_event.dropped` > 0 | 高 |
| 连接池 | 前台池使用率 > 80% 持续 5 分钟 | 中 |
| 通知投递 | 最老待投递 > 10 分钟；失败率 > 10% | 中 |
| 审计读写 | `audit.read_write_failures` > 0 | 中 |
| 容量保护 | `admission.state` = 2（硬线） | 紧急 |
| 容量保护 | `admission.state` = 1（软线） | 高 |
| 容量判断失效 | `sample_age_seconds` 超过 3 个采样周期；`capacity_age_seconds` > 1 天 | 高（样本过期时熔断状态维持不变，必须有人处理） |
| 待终结订阅 | 待终结超过补投窗口 R 仍未终结 | 中（提醒） |
| 读模型 | `terminal_conflicts` > 0；`rebuild_paused` > 0 | 中 |
| 提交结果未知 | `commit.outcome_unknown` > 0（含定时任务执行记录为 `Unknown`） | 中 |
| 外部调用结果未知 | `external_call.unknown` > 0 | 中 |
| 文件待还原 | `files.restore_pending` > 0 | 高 |

- 与应用无关的兜底告警（RDS 存储使用率等）在云监控中配置，见 09 第 11 节。

## 6. 健康检查

### 6.1 端点

| 端点 | 检查 | 用途 |
|---|---|---|
| `/health/live` | 只检查进程能响应（不检查任何依赖） | 编排平台判断是否需要重启容器 |
| `/health/ready` | 见 D4 | 编排平台 / 反向代理判断是否把流量发给它 |
| `/health/dependencies` | 全部依赖的详细状态（数据库、Redis、对象存储、SMTP、短信网关、监听连接、Quartz） | 运维与监控；**只在内部端口 / 内网可访问**（不提供需要权限点的页面，依赖状态留给内网端点与观测平台；Operations 设计 D-O1） |

- `/health/live`、`/health/ready` 匿名，只返回 `Healthy` / `Unhealthy`，不返回细节；反向代理不对公网暴露 `/health/*`（ADR-0022）。
- 只跑 Worker 的实例同样提供三个端点（05-08 第 3.1 节）。

### 6.2 D4 就绪检查包含哪些依赖

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 只检查“没有它整个服务无法工作”的条件** | 数据库可连接；启动任务已完成；未处于停机中 | 对象存储、SMTP 等局部依赖故障时，实例仍接收请求，其余功能正常；不会因一个外部依赖抖动导致全部实例被摘除 | 依赖局部故障时，相关功能的请求会失败（返回 503 `retryable`），需要靠 `/health/dependencies` 与告警发现 |
| B 检查全部依赖 | 任一依赖失败即不就绪 | 状态直观 | 对象存储故障 → 所有实例同时不就绪 → 整个系统不可用，把局部故障放大成全局故障 |

- **决定（已确认，2026-11-04）**：A。
- **理由**：就绪检查的含义是“把流量给我是否有意义”，而不是“我的所有依赖都好”。
- **取舍**：局部依赖故障不会在就绪状态上体现，必须有依赖状态的告警。
