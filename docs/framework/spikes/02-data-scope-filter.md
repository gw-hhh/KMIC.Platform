# 原型 #2：用 EF Core 10 命名查询过滤器实现数据范围

- 状态：结论已得出；D1、D2 待决（2026-11-06）
- 来源：08 第 4 节原型 #2（阻断）；05-05 第 5.4 节“`待确认`：EF 10 命名过滤器中对上下文成员方法调用的参数化行为、Npgsql 对强类型 ID 数组参数（`= ANY`）的转换”
- 原型代码：分支 `spike/02-ef-datascope` 的 `spikes/02-ef-datascope/`（与原型 #4 共用；查询计划的脚本在 `plans/`；一次性代码，不合入主干）
- 环境：.NET SDK 10.0.403；EF Core 10.0.14；Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3；PostgreSQL 18（Docker 镜像 `postgres:18`，测试经 Testcontainers 4.16.0 启动）

## 1. 结论

**成立。** 05-05 第 5.4 节的写法在 EF Core 10 + Npgsql 10 + PG 18 上按设计工作，`待确认` 关闭，不需要启用备选方案（显式 `IQueryable` 扩展）。另有三个发现：过滤器要用的“当前用户”在 05-05 中没有来源（D1）；数据范围查询依赖 PG 按实际参数值做计划（D2）；关系可见的 `OR EXISTS` 用不上索引（第 3 节）。

| 要求 | 结论 | 依据 |
|---|---|---|
| 过滤器经上下文成员读取范围，取值来自执行查询的上下文 | 成立 | 两个范围不同的上下文生成相同的 SQL，参数分别取各自的值 |
| 范围值是参数，不拼进 SQL | 成立 | SQL 中没有任何 ID 字面量 |
| 不同范围的同一查询只编译一次 | 成立 | 三个不同范围的上下文共用一份选项执行同一查询，`QueryCompilationStarting` 只出现 1 次 |
| 强类型 ID 列表作为一个数组参数 | 成立 | `IReadOnlyList<OrgUnitId>` 绑定为一个 `uuid[]` 参数，翻译为 `= ANY (@…)`；空列表结果正确 |
| 关系可见（`EXISTS`）、资源可见性 | 翻译正确，结果正确 | 查询计划有问题，见第 3 节 |
| 只忽略数据范围，软删除仍生效 | 成立 | `IgnoreQueryFilters(["DataScope"])` |
| 系统身份（没有当前用户） | 成立 | 返回全部未删除的数据 |
| 强类型 ID 键集分页 | 成立 | `s.Id.CompareTo(cursor) < 0` 翻译为 `"Id" < @cursor`；PG `uuid` 的排序与 .NET `Guid` 的比较顺序一致（v7 ID 实测） |

离线 SQL 检查 6 项、PG 18 上 7 项，共 13 项测试全部通过，连续运行 3 次结果相同。

普通用户的查询生成的条件（参数名由 EF 生成）：

```sql
WHERE NOT (s."IsDeleted")
  AND (@ef_filter__DataScopeUnrestricted7
       OR ((NOT (s."IsPrivate") OR s."OwnerId" = @ef_filter__DataScopeCurrentUser)
           AND (@ef_filter__All4
                OR s."OwnerId" = @ef_filter__Owner
                OR s."OrgUnitId" = ANY (@ef_filter__OrgUnits)
                OR EXISTS (
                    SELECT 1 FROM sample."SampleCollaborator" AS s0
                    WHERE s."Id" = s0."SampleId" AND s0."UserId" = @ef_filter__DataScopeCurrentUser0))))
```

## 2. 实现要点（阶段 2 照此实现）

| 要点 | 说明 |
|---|---|
| 声明与注册分两步 | `HasDataScope` 只把声明记在实体的模型注解上；模块配置全部完成后，`ModuleDbContext` 统一为这些实体注册 `DataScope` 命名过滤器。原型的做法是基类的 `OnModelCreating` 设为 `sealed`，先调用模块的模型配置方法，再注册过滤器；阶段 2 与 05-03 的上下文基类一起定 |
| 占位符替换 | 关系可见、资源可见性的表达式中写 `DataScopeParam.CurrentUser`，注册过滤器时替换为上下文成员（来源见 D1）；业务模块的写法与 05-05 第 5.4 节完全一致 |
| `IDataScope.For` 每个查询调用 3 次 | EF 把 `All`、`Owner`、`OrgUnits` 三个成员访问分别求值为参数，每次都调用一次 `For`。05-05 第 5.3 节已规定请求内缓存，实现必须做到，并有测试覆盖“同一请求多次调用只计算一次” |
| 参数为空时的 SQL | 当前用户为 `null`（系统身份）时，EF 去掉 `= NULL` 的分支，生成另一份 SQL。这是 EF 按参数是否为空缓存的 SQL 变体，不会重新编译查询 |
| `static readonly` 字段被内联 | 查询中直接引用 `static readonly` 字段，EF 10 把它当作常量写进 SQL（实测 `s."Id" < '019a…'`）。只适合真正的常量；请求值（游标、筛选条件）来自参数或局部变量，自然是 SQL 参数 |
| 测试编译次数的写法 | 同一份选项创建的上下文共用查询缓存，同一夹具里的其他测试可能已经编译过同样的查询。这类测试要用其他测试不会用到的查询形状。原型中原写法单独运行通过、整体运行时计数为 0，已改正 |

## 3. 查询计划（PG 18 实测）

数据：20 万行，200 个组织单元、2000 个用户，10% 私有；`OwnerId`、`OrgUnitId` 各有索引，关联表有 `(UserId, SampleId)` 索引（05-05 第 5.8 节）。当前用户可见 187～1100 行。关闭并行查询。

| 情况 | 计划 | 执行时间 |
|---|---|---|
| 只有所属人、组织两个分支，按实际参数值做计划（custom plan） | 两个索引的 BitmapOr | 1.6 ms |
| 同上，预备语句的通用计划（generic plan） | 全表扫描 | 12.8 ms |
| 加上关系可见的 `OR EXISTS (…)`，计数 | 全表扫描 | 34 ms |
| 同上，列表页（`ORDER BY "Id" LIMIT 20`），只看本人 | 沿主键索引逐行过滤 | 4.5 ms |
| 关系条件改写为 `"Id" = ANY (ARRAY(SELECT …))`，计数 | 三个索引的 BitmapOr | 0.17 ms |

时间是单次运行的结果，在新容器上重跑脚本时有波动（如第一行 1.0 ms、第三行 41 ms、第四行 11 ms），计划和结论不变。

1. **数据范围依赖按实际参数值做计划。** 过滤器中的 `@unrestricted OR …`、`@all OR …` 只有在计划时知道参数值才能被消去，消去之后所属人、组织两个分支才能用索引组合。通用计划不知道参数值，只能全表扫描，表越大差距越大。Npgsql 默认不自动预备语句（`Max Auto Prepare = 0`），EF 也不预备命令，每次执行都按实际值做计划（实测计划耗时约 0.3 ms），所以默认行为正好满足要求。D2 把它定为规则，防止以后为了省计划时间而开启。
2. **关系可见的 `OR EXISTS` 用不上索引。** PG 把 `OR` 中的 `EXISTS` 改为哈希子计划，整个 `OR` 不能再拆成索引组合：计数和导出会全表扫描；列表页沿主键索引逐行过滤，可见数据越稀疏、表越大越慢。把关系条件写成 `"Id" = ANY (ARRAY(SELECT "SampleId" FROM … WHERE "UserId" = @me))` 后三个分支都能走索引。EF 不会直接生成这种写法，需要自定义翻译。关系可见本来就延后到第一个需要它的业务模块（05-05 第 5.8 节），实现时一并解决，已在 00-README 的延后事项中补充这条约束。

## 4. 待决事项

### D1 过滤器中的“当前用户”从哪里取（待决，补充 05-05 第 5.3、5.4 节）

关系可见与资源可见性都要知道“我是谁”（`DataScopeParam.CurrentUser`），但 05-05 第 5.3 节的 `IDataScope` 只有 `Unrestricted` 和 `For`，没有当前用户；范围是“全部”时 `EffectiveScope.Owner` 不一定有值，不能借用。原型临时在 `IDataScope` 上加了 `CurrentUser`。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 从执行上下文取** | 占位符替换为 `ModuleDbContext` 上的成员，读取 `IExecutionContext.User.UserId`（05-02 第 7.1 节；系统身份为 `null`，模拟登录时是被模拟的用户） | 身份只有一个来源；`ModuleDbContext` 本来就依赖 `IExecutionContext`（选择数据源、写审计列），不增加依赖；`IDataScope` 不变 | 过滤器同时依赖两个服务，过滤器测试要准备两个替身 |
| B `IDataScope` 增加 `UserId? CurrentUser` | 实现中同样取自 `IExecutionContext` | 过滤器只依赖 `IDataScope` 一个服务 | 同一个身份在两个接口上各有一份；测试替身可能给出不一致的值（范围按 A 用户算、关系按 B 用户查），接口的职责也从“范围”扩大到“身份” |

- **建议**：A。
- **理由**：当前用户已经有标准来源，再复制一份只会多一个出错的地方。
- **取舍**：过滤器测试多准备一个执行上下文的替身（阶段 2 的测试基座本来就提供）。

### D2 不开启 Npgsql 自动预备语句（待决，补充 05-03 第 2.1 节）

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 保持默认，不开启，并写成规则** | 05-03 写明；注册数据源时检查连接串，开启了就启动失败 | 每次按实际参数值做计划，数据范围能用索引（第 3 节） | 每次执行多一次计划（实测约 0.3 ms） |
| B 开启，同时把运行账号的 `plan_cache_mode` 设为 `force_custom_plan` | 省去语句解析，仍按实际值做计划 | 省一点解析时间 | 收益很小；正确性依赖一项数据库账号配置，漏设时不报错，只是悄悄变慢 |
| C 开启，计划模式用默认的 `auto` | PG 执行 5 次后可能改用通用计划 | 省去计划时间 | 实测通用计划下数据范围查询变为全表扫描 |

- **建议**：A。
- **理由**：计划耗时远小于用不上索引的代价；启动时检查让这条规则不靠记忆。
- **取舍**：放弃预备语句带来的那一点解析和计划时间。
