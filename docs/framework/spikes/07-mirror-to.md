# 原型 #7：迁移过渡映射 `.MirrorTo(...)` 与列改名的发布顺序

- 状态：结论已得出；D1 待决（2026-11-06）
- 来源：08 第 4 节原型 #7（非阻断）；06 第 11.3 节“`待确认` 实现方式”
- 原型代码：分支 `spike/06-07-10-ef-and-testing` 的 `spikes/06-07-10-ef-and-testing/`（与原型 #6、#10 共用；一次性代码，不合入主干）
- 环境：EF Core 10.0.14；Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3；PostgreSQL 18

## 1. 结论

**`.MirrorTo(...)` 可以实现，`待确认` 关闭；但 06 第 11.3 节列改名示例的发布 1 读错了列，需要修订（D1）。**

实现：`.MirrorTo("列")` 为实体加一个映射到该列的影子属性，并在属性上记一个注解；一个保存拦截器在保存前把属性的当前值复制到影子属性（新增时总是复制，修改时只在该属性被修改时复制）。读取只用属性映射的列。

| 场景 | 结果 |
|---|---|
| 新增、修改 | 两列都写入相同的值 |
| `ExecuteUpdate` 批量更新 | **不经过保存拦截器，另一列不会同步**（实测新列为“批量”、旧列仍是原值） |
| 06 原写法的发布 1（读新列、写两列），滚动期间上一版修改了一行 | 读到**旧值** |
| 同上，滚动期间上一版新建了一行（只写了旧列） | 新列为空，属性不可空，**读取直接抛异常**（`InvalidCastException`），列表与详情会返回 500 |
| 修订后的发布 1（仍读旧列、写两列） | 读到上一版写入的值；本版的修改两列都写，上一版也能读到 |
| 修订后的发布 2（上一版已全部退出，再次回填后改读新列） | 读到正确的值 |

4 项测试通过，连续运行 3 次结果相同。

## 2. 待决事项

### D1 列改名示例改为“发布 1 仍读旧列”（待决，修订 06 第 11.3 节示例一）

问题：发布 1 滚动期间，上一版代码仍在运行，并且只写旧列。06 原写法让发布 1 的代码读新列，那么上一版在这几分钟里修改或新建的行，本版读到的就是旧值或空值；空值落在不可空的属性上会直接抛异常。原写法“上一版只读写 `Name`，本版两列都写、读新列 → 可以”的判断不成立。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 读切换推迟一个发布** | 发布 1：加新列、回填；代码**读旧列**、写两列（属性映射到旧列，`.MirrorTo("新列")`）。发布 2：再次回填，新列改为非空；代码改为**读新列**、仍写两列（`.MirrorTo("旧列")`）。发布 3：停写旧列。发布 4：删除旧列 | 每个发布的读取都只依赖“所有运行中的代码都会写”的列，滚动期间不会读到旧值或空值 | 发布 1 中实体属性名（`DisplayName`）与列名（`Name`）暂时不一致，映射中要显式写列名 |
| B 发布 1 读新列，读不到时退回旧列 | 映射成计算值或在查询中写 `COALESCE` | 读切换早一个发布 | EF 的属性映射不支持“读两列取其一”；每个查询都要手写，容易漏 |
| C 维持原写法，接受滚动期间的错误 | — | 不改文档 | 滚动更新期间会出现 500 和读到旧值，违背 NFR-AVAIL 对滚动更新的要求 |

- **建议**：A；示例二（拆表）同样按“先写两处、再切换读取”的顺序，已经是这样写的，不需要改。
- **理由**：扩展 / 收缩模式的要点是“读取只能依赖所有运行中的代码都会写的数据”；原写法在发布 1 违反了这一点。
- **取舍**：发布 1 中属性名与列名暂时不一致。
- **随之明确的规则**：过渡期间，带 `.MirrorTo` 的属性**不得用 `ExecuteUpdate` 批量更新**，确需批量更新时在同一条语句中两列都写；由架构测试检查（扫描 `ExecuteUpdate` 中对带 `MirrorTo` 注解属性的 `SetProperty`）。
