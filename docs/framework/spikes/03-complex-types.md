# 原型 #3：值对象的四种映射形态与审计所需的原值

- 状态：结论已得出；D1、D2 待决（2026-11-06）
- 来源：08 第 4 节原型 #3（阻断）；05-03 第 3.4 节“`待确认`：Npgsql 10 对可选复杂类型、复杂类型集合映射为 `jsonb` 的支持程度”；05-09 第 9 节“EF Core 10 变更跟踪器对复杂类型（值对象、`jsonb` 集合）原值的获取方式”
- 原型代码：分支 `spike/03-complex-types` 的 `spikes/03-complex-types/`（一次性代码，不合入主干）
- 环境：.NET SDK 10.0.403；EF Core 10.0.14；Npgsql.EntityFrameworkCore.PostgreSQL 10.0.3；PostgreSQL 18（Testcontainers）

## 1. 结论

**05-03 第 3.4 节的四种映射在 Npgsql 10 + PG 18 上都可行，审计需要的原值也都拿得到，`待确认` 可以关闭；但按 05-01 原定的写法映射不上，需要改两处写法（D1、D2）。** 不需要启用 05-03 的备选方案（单值转换器或 JSON 值转换器）。

| 形态 | 结论 | 实测 |
|---|---|---|
| 多值值对象 → 复杂类型，每个成员一列 | 成立 | `CreditLimitAmount numeric(18,2)`、`CreditLimitCurrency varchar(3)` |
| 可空的多值值对象 → 可选复杂类型 | 成立 | 空 → 有值 → 空，往返正确；值对象至少要有一个不可空成员（第 3 节） |
| 值对象集合 → 复杂类型集合存为 `jsonb` | 成立，但要映射私有字段（D2） | 增、改、删元素都能保存；元素中嵌套的可选值对象也能存取 |
| 单值值对象 → 一列 | 成立 | 框架约定 + 泛型转换器，`Email varchar(256)`；查询中的值对象参数自动转换 |
| 列名“属性名 + 成员名”，不带下划线（05-03 第 3.1 节） | 成立 | 一个模型约定统一处理，实体配置中不用逐个写列名 |
| 读库时不经过工厂方法的校验（05-01 第 5.3 节） | 成立 | 数据库中写入现在会被拒绝的旧值（`legacy`、`-1`），照样能加载 |
| 审计取得修改前的值（05-09 第 3.3 节） | 成立 | 见第 2 节 |
| 查询值对象的成员 | 成立 | 复杂类型成员直接成为列条件；`jsonb` 集合内的条件翻译为 `EXISTS (… jsonb_to_recordset …)` |

PG 18 上 8 项测试全部通过，连续运行 2 次结果相同。

## 2. 审计：变更跟踪器中的原值

05-09 第 3.3 节拦截器 6 的核心逻辑在原型中实现为 `ChangeCollector`，对同一个客户同时修改四种值对象后得到：

```text
Email: old@example.com → new@example.com
CreditLimit.Amount: 100.00 → 200
ShippingAddress.City: null → 杭州
ShippingAddress.Street: null → 文三路 1 号
Contacts: [{"Name":"甲","Phone":null,"CreditLimit":null}] → [{"Name":"甲","Phone":"13800000000","CreditLimit":null}]
```

| 形态 | 怎么取原值 |
|---|---|
| 普通属性、单值值对象 | `entry.Properties` 中 `IsModified` 的属性，`OriginalValue` / `CurrentValue`；单值值对象用属性上的转换器转为原始值再记录 |
| 复杂类型（含可选） | `entry.ComplexProperties` → 逐个成员的 `OriginalValue`，嵌套的复杂类型递归处理；可选值对象由空变为有值（或相反）时，表现为各成员由 `null` 变为有值，未变的成员（两边都是 `null`）不记录 |
| 复杂类型集合 | `entry.ComplexCollections` 中 `IsModified` 的集合；`ComplexCollectionEntry` 没有 `OriginalValue`，整体原值用 `entry.OriginalValues[集合的元数据]` 取得，与当前值一起序列化，符合 05-09“集合只记录前后整体值” |

实现时注意：

- 小数的原值来自数据库，带列的小数位（`100.00`），新值是程序中的写法（`200`）。比较按数值，不会误报；但记录的文字格式不同，拦截器 6 应按列的精度统一格式化。
- 映射到私有字段的集合（D2），元数据名是 `_contacts`，审计中要用列名（`GetContainerColumnName()`）。

## 3. 其他发现

| 发现 | 说明 |
|---|---|
| 可选值对象至少要有一个不可空成员 | 全部成员都可空时，EF 无法区分“值对象为空”和“值对象的成员都为空”，**构建模型时直接报错**，提示加一个必填成员或配置判别列。不会悄悄存错 |
| `jsonb` 中的属性名 | 用 CLR 名称（`"Name"`、`"CreditLimit": {"Amount": …}`），与表的大驼峰列名一致 |
| `jsonb` 集合内的查询用不上普通索引 | 翻译为 `EXISTS (SELECT … FROM jsonb_to_recordset(…))`。偶尔按元素筛选可以；经常要按元素查询、统计的数据，应建成子实体（独立的表），不要放进值对象集合。05-03 第 3.4 节补充这条选择依据 |
| 单值值对象的约定 | 扫描 Domain 程序集中实现 `ISingleValueObject<T>` 的类型，统一注册泛型转换器；转换器调用私有构造函数（表达式树），不用 `public` 的“跳过校验”入口 |

## 4. 待决事项

### D1 值对象的属性写成 `{ get; private init; }`（待决，修订 05-01 第 5.1 节 KM0203）

05-01 规定值对象的属性“只能是 `{ get; }`，不得有 `set` / `init`”（KM0203）。但 **EF 按约定只映射有 setter 的属性**（setter 可以是私有的），只有 getter 的属性不会被映射。实测：

- 集合元素 `ContactPerson` 的 `Name`、`Phone` 都没有被映射，元素中嵌套的 `Money` 一个成员都没有，构建模型时报“没有任何属性”。
- 更危险的是**只漏掉部分成员时不会报错**，那些成员就是不保存。顶层的 `Money`、`Address` 能用，只是因为原型中逐个配置了每个成员。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 属性写成 `{ get; private init; }`** | KM0203 改为：值对象属性必须是 `{ get; private init; }`，不得有 `set`，`init` 只能是 `private` | EF 按标准约定映射全部成员，不需要任何配置，也没有漏映射的可能；`private init` 在类型外不可访问，**`with` 表达式仍然无法绕过校验**（实测：类型外写 `money with { Amount = -1m }` 编译失败 CS0200） | 类型内部仍可用 `with`（只影响值对象自己的代码，可接受）；属性写法比 `{ get; }` 长一点 |
| B 保持 `{ get; }`，每个成员在映射中逐个配置 | 05-01 不变 | 值对象写法最简 | 每个值对象的每个成员都要写一行映射，集合元素、嵌套值对象也一样；需要另加启动校验检查“值对象的公开属性都已映射”，否则漏掉的成员悄悄不保存 |
| C 保持 `{ get; }`，框架写约定自动映射只读属性 | 框架遍历复杂类型，把只读自动属性按编译器生成的字段映射 | 值对象写法最简，不需要逐个配置 | 要自己判断成员是普通列还是嵌套值对象、集合，等于重写一部分 EF 的约定；未验证 |

- **建议**：A。
- **理由**：A 让值对象回到 EF 的标准行为，原来 KM0203 要防的“`with` 绕过校验”照样防得住；B、C 都是为了保住 `{ get; }` 这个写法而多出配置或框架代码，还要额外防漏。
- **取舍**：值对象属性多写 `private init`；分析器 KM0203 按新规则实现。

### D2 聚合中的值对象集合映射私有字段（待决，补充 05-03 第 3.4 节）

**EF 10 的复杂类型集合要求属性类型实现 `IList<T>`**，而 05-01 规定聚合的集合只能以 `IReadOnlyList<T>` 公开（KM0105）。实测：直接映射公开属性在构建模型时报错，指定后备字段（`HasField`）也不行，EF 检查的是公开属性本身的类型。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 映射私有字段** | 聚合照旧写 `private readonly List<ContactPerson> _contacts` + `public IReadOnlyList<ContactPerson> Contacts => _contacts`；映射时忽略公开属性，按名称映射字段，列名用公开属性名：`builder.Ignore(c => c.Contacts); builder.ComplexCollection<List<ContactPerson>, ContactPerson>("_contacts", c => c.ToJson("Contacts"))`。框架把这两行包成一个扩展方法（如 `builder.ValueObjectCollection(c => c.Contacts)`，按命名约定找字段） | 领域写法不变，KM0105 不变；保存、加载、审计、查询都实测可行 | 在查询中筛选集合内容要写 `EF.Property<List<ContactPerson>>(c, "_contacts")`（字符串字段名）；这类查询本来就应该很少（第 3 节） |
| B 公开属性改为 `IList<T>` | 直接映射 | 查询写法自然 | 外部可以直接增删集合元素，绕过聚合的规则；违反 KM0105 |
| C 改用 JSON 值转换器 | 公开属性加转换器，整个集合作为一个值 | 公开属性可以直接映射 | 不能查询集合内容；嵌套值对象要靠 System.Text.Json 构造，私有构造函数需要另外处理；就是 05-03 原来的备选方案，能力比 A 少 |

- **建议**：A。
- **理由**：领域模型的封装比查询写法重要；A 只在少见的“按集合元素筛选”时多写一个字段名。
- **取舍**：按元素筛选的查询要用字段名；EF 以后支持只读集合类型时，改回直接映射公开属性（登记实施待办，升级 EF 大版本时复查）。
