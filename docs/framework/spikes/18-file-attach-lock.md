# 原型 #18：附件关联与到期清理按文件 ID 加锁互斥

- 状态：结论已得出，成立；没有待决事项（2026-11-06）。05-11 第 3.3 节的关联与清理协议由“设计候选”转为实施依据
- 来源：08 第 4 节原型 #18（阻断）；R02-3；05-11 第 3.3、4.3 节的 R02 补充说明
- 原型代码：分支 `spike/18-file-attach-lock` 的 `spikes/18-file-attach-lock/`（一次性代码，不合入主干）
- 环境：Npgsql 10.0.3；PostgreSQL 18（Testcontainers，独占的临时实例）

## 1. 做法

08 第 4 节要求：独占临时实例、只让目标业务会话等待同步复制、到期条件在数据库侧构造。实现为：

- 实例级设置 `synchronous_standby_names` 为一个不存在的备库名；所有普通连接用 `synchronous_commit = local`，只有被测的业务事务 `SET LOCAL synchronous_commit = on`。这个事务提交时就停在“等待同步复制”（`pg_stat_activity.wait_event = 'SyncRep'`，测试先确认这一点再继续），清空设置后立即完成提交。
- 文件的到期时间写成 `clock_timestamp() + 1 秒`，清理按 `"ExpiresAt" < clock_timestamp()` 筛选，全部用数据库时钟。
- 业务关联、清理按 05-11 第 3.3 节补充说明的步骤原样实现：共享 / 排他事务级咨询锁（键为 `SHA-256("Kmic.Files:" + 文件 ID)` 的前 8 字节）、取锁后读最新状态、先探查 Outbox 再探查 Files Inbox 中未完成的 `AttachFiles`（`SubjectIds` 的 GIN 部分索引）、带状态条件改为 `Deleting`。

## 2. 结论

**成立。** 协议依赖的 PG 行为得到确认：**提交停在等待同步复制时，事务级咨询锁仍被持有，提交对其他会话也还不可见；锁在提交变为可见之后才释放。** 在这个前提下协议的每一步都按设计工作；只按时间判断的旧写法（对照组）确实会删掉正在关联的文件。

| 场景 | 结果 |
|---|---|
| 业务事务取共享锁、检查、写关联与 `AttachFiles` 后提交，提交停在等待同步复制；期间文件跨过到期时刻 | 关联行对其他会话不可见；清理取不到排他锁，**跳过**，文件仍是 `Available` |
| 上一场景释放同步复制等待、提交完成后再次清理 | 能取到锁，但探查到 Outbox 中未完成的 `AttachFiles`，**跳过**；消息投递、处理后文件变为 `Attached`，此后不再是清理候选 |
| 释放等待的同时反复尝试取排他锁 | 第一次取到锁时，业务提交（Outbox 中的消息）**已经可见** |
| 对照组：同样停在提交阶段，清理只按到期时间判断 | 文件被改为 `Deleting`；业务提交后，关联行指向一个正在删除的文件，`AttachFiles` 的处理改不到它 |
| 清理先取得排他锁并把文件改为 `Deleting`（未提交）时业务开始关联 | 业务在取共享锁处等待（`wait_event = 'advisory'`）；清理提交后业务取得锁，读到 `Deleting`，关联被拒绝 |
| 清理持有排他锁期间业务关联，锁等待上限 1 秒 | 业务得到 `55P03 lock_not_available`（框架映射为 503 `Common.TransientConflict`，`retryable`） |
| 清理的三步（探查 Outbox、探查 Inbox、带条件标记）与 `AttachFiles` 投递的三步（写入 Files Inbox、标记 Outbox 已投递、处理）的**全部 20 种交错** | 按文档的顺序（先 Outbox、后 Inbox）**0 种**误删 |
| 对照组：先探查 Inbox、后探查 Outbox | 20 种交错中 **1 种**误删：先查 Inbox 时消息还没到，再查 Outbox 时消息已标记为已投递，两边都查不到 |

共 26 项测试（其中探查顺序 20 项、两个对照组），全部通过，连续运行 3 次结果相同。

## 3. 说明

- 本原型验证的是协议在数据库层面的正确性。`IFileAttachments.AttachAsync` 的框架入口、分析器拦截直接 `Send(AttachFiles)`、50 个文件的上限，以及“引用 `Available` / `Detached` 文件的 `AttachFiles` 不能人工放弃”，在阶段 2～3 实现 Files 模块时完成，不影响本结论。
- 原型中 Files Contracts 的可关联性检查用另一个连接读取（对应读池），与业务事务不是同一个连接；这正是设计中的形态：共享锁由业务事务持有，检查读的是锁之后的最新已提交状态。
- 退路“引用探查”（05-11 第 3.3 节规则表最后一行）不需要启用。
