# 原型 #17：读模型终态不被迟到的数据复活

- 状态：结论已得出，成立；没有待决事项（2026-11-06）
- 来源：08 第 4 节原型 #17（阻断）；05-07 第 8.1～8.4 节的 R02 补充说明；05-07 第 11 节 R02 补充的读模型场景
- 原型代码：分支 `spike/16-17-messaging` 的 `spikes/16-17-messaging/`（与原型 #16 共用；一次性代码，不合入主干）
- 环境：Npgsql 10.0.3；PostgreSQL 18（Testcontainers）

## 1. 结论

**成立。** 05-07 R02 补充说明中读模型的三种写入（实时事件、物理删除快照、重建扫描）、重建收尾与保护阈值，在 PG 18 上按设计工作。关键点是：三种写入都是一条 `INSERT … ON CONFLICT DO UPDATE … WHERE NOT "IsTerminal"`，**在两个事务并发时，后到的一方会等待先到的一方提交，再按提交后的最新行重新判断条件**，所以不会凭旧数据把终态改回来。

| 场景 | 结果 |
|---|---|
| 重建扫描先读到存在快照（v1）→ 来源物理删除，物理删除快照（v2）先写入 → 迟到的存在快照写入 | 不修改，返回“未写入”（调用方据此记“终态但源端返回”的异常）；行保持终态，版本 v2 |
| 同上，但物理删除快照的事务尚未提交时扫描写入到达（行已存在 / 行还不存在两种） | 扫描写入**等待锁**（实测在 `pg_stat_activity` 中处于锁等待），物理删除提交后扫描写入不修改；不复活 |
| 反过来：扫描写入先进行、未提交时物理删除快照到达 | 物理删除等待，扫描提交后照常置终态 |
| 实时事件版本更低、相同、更高 | 只有更高的版本写入 |
| 1000 行版本未变，其中 10 行内容被改坏；另一行已有更新的实时版本（v5） | 重建后 0 行被置终态；改坏的内容被修复；全部 1000 行写入本轮轮次；v5 的行不降版本、内容不被旧数据覆盖 |
| 收尾：一行在来源被物理删除但事件丢失；一行在扫描越过之后才新建（只经实时事件写入）；一行在“选为候选之后、置终态之前”收到物理删除快照 | 丢事件的行置终态（`ConfirmedMissing`）；后建的行经源端确认存在，不置终态；第三行的条件更新影响 0 行，保持 `PurgeEvent` |
| 来源实现有缺陷，分页与按 ID 读取都返回空（300 行全部成为候选） | 超过保护阈值（`max(100, 1%)`），本轮暂停为“待确认”，**0 行**被置终态 |
| 同一读模型同时启动两轮重建 | 第二轮因部分唯一索引失败（`23505`） |

共 9 项测试，全部通过，连续运行 3 次结果相同。

## 2. 说明

- 重建扫描的“本地版本 ≤ 扫描版本时覆盖全部字段，否则只写轮次”用一条语句完成：`SET "SourceVersion" = GREATEST(…)`、各字段用 `CASE WHEN r."SourceVersion" <= EXCLUDED."SourceVersion"` 选择新旧值、`"RebuildRunId"` 总是写入，条件只有 `WHERE NOT r."IsTerminal"`。返回 0 行即说明该行是终态。
- 原型的重建没有实现作业租约与检查点（05-08 第 6.4 节），那部分由原型 #16 同样的“令牌 + 带条件更新”保证，不在本原型范围内。
