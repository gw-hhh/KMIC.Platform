## 1. 结论

**成立。** R01 H1 的结构（命令只持有一个事务池连接，嵌套读取一律走读池）在高并发下不会自锁；单池的对照组按预期自锁。验证中发现两个相关问题，需要补充设计（D1、D2）。

| 场景 | 结果 |
|---|---|
| 单池（上限 5），5 个命令同时持有事务连接后各发一次嵌套读取 | **全部借连接超时**：每个命令占着一个连接、等第二个（对照组，证明问题真实存在） |
| 事务池 5 + 读池 1，同样的 5 个命令 | 全部完成 |
| 事务池 5 + 读池 2，40 个命令同时提交 | 全部完成（排队，不自锁） |
| 查询处理器：查询 → 经 Contracts 查询另一个模块 → 再查询，读池只有 1 个连接 | 完成：EF 的查询上下文每次查询完就归还连接，两次查询之间不占连接 |
| 流式枚举（`AsAsyncEnumerable`）期间发起另一个查询，读池 1 个连接 | **借连接超时**：流式读取在整个枚举期间占着连接 |
| 同上，查询启用重试执行策略 | 同样超时：启用重试策略后流式查询**不会**先读入内存 |
| 读池已满时查询，EF 默认的重试策略 | 借连接超时被当作暂时性故障，**重试 6 次，65 秒后才失败** |
| 同上，框架的查询重试策略（D1） | 不重试，1 秒（即一次借连接超时）后失败 |
| 导出在单独的流式池上逐行读取，期间的其他查询走读池（D2） | 完成 |

9 项测试全部通过。

H1 成立依赖的前提也得到确认：EF 的查询上下文不在两次查询之间持有连接；事务行为开启事务后，写入上下文从开启到提交只占一个事务池连接。

## 2. 待决事项

### D1 查询的重试策略不重试“借连接超时”，并限制总等待（已确认 2026-11-10，补充 05-02 D4）

05-02 D4 定了“查询启用 EF 的重试执行策略”。EF 的默认策略（Npgsql 版）最多重试 6 次、单次退避最长 30 秒，并且把**借连接超时**也当作暂时性故障。借连接超时说明的是应用自己已经饱和，这时重试只会让每个请求多等一分钟以上、排队越来越长，而不是让请求成功。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 框架自己的查询重试策略** | 继承 `NpgsqlRetryingExecutionStrategy`：借连接超时不重试；最多重试 2 次、单次退避最长 1 秒；其余暂时性故障（连接断开、主备切换等）照常重试 | 饱和时快速失败，返回 503 `retryable`，前端按 05-02 D4 的约定稍后重试；真正的瞬时故障仍然透明 | Npgsql 没有“借连接超时”专门的异常类型，只能按消息识别；用测试固定这段消息，升级 Npgsql 时会发现变化 |
| B EF 默认策略 | 不改 | 不写代码 | 饱和时每个查询最多等一分多钟，雪崩时放大排队 |
| C 查询也不重试 | 和命令一样 | 最简单 | 连接断开、主备切换这类真正的瞬时故障也直接暴露给用户 |

- **建议**：A。
- **理由**：重试是为了跨过数据库端的短暂故障，不是为了等应用自己的连接池；两者要分开处理。
- **取舍**：多一个框架类，以及一处依赖异常消息的识别（有测试守住）。

### D2 导出的流式读取使用单独的“流式池”（已确认 2026-11-10，补充 05-03 第 2.1 节、05-08 第 6.8 节）

05-08 规定导出用 `AsAsyncEnumerable` 流式读取，避免把全部数据读入内存。流式读取在整个导出期间占着一个读池连接；导出过程中只要再发起任何查询（Contracts 查询、字典或系统设置的缓存未命中等），就需要同一个池的第二个连接。同时运行的导出数达到读池上限时，与 H1 是同一种自锁。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A Worker 增加一个流式池** | 只有导出的主查询在流式池上执行（`kmic-worker-stream`，上限 = 同时运行的导出数）；导出期间的其他查询照常走读池。流式池的连接可以等读池，读池的连接从不等别人，不成环 | 与 H1 同样是“结构上不可能自锁”；导出照常流式读取，内存占用不变 | Worker 多一个数据源（5 个）和一项配置；框架要提供“在流式池上执行导出主查询”的入口（导出作业的基类负责），业务代码不能自行 `AsAsyncEnumerable` |
| B 规定“流式读取期间不得发起其他查询” | 评审 + 开发与测试环境的运行时守卫 | 不增加数据源 | 缓存未命中这类隐藏的查询很难避免；守卫只能在测试碰到时发现 |
| C 导出改为分页读取 | 每页读入内存后再处理，页与页之间不占连接 | 不需要新数据源 | 任意排序下的键集分页实现复杂；偏移分页在导出期间数据变化时会重复或漏行 |

- **建议**：A。流式读取只能经框架的导出入口，Application 中其他地方使用 `AsAsyncEnumerable` 由禁用 API 检查拦截。
- **理由**：与 R01 H1 的判断一致：靠规则和参数不如从结构上排除。
- **取舍**：多一个数据源；导出主查询的写法受框架入口约束。
