## 3. 发现：Windows 上 Npgsql 的异步监听等待不响应超时

本机运行时 `LISTEN / NOTIFY` 的测试卡住，单独对比后确认（对比脚本 `probes/listen-wait.cs`）：

| 等待写法 | Windows（本机，经 Docker Desktop 连容器） | Linux（.NET SDK 容器内，同一个 PG） |
|---|---|---|
| `WaitAsync(TimeSpan)` 500 ms | 5 秒后仍未返回 | 507 ms 返回 `false` |
| `WaitAsync(int)` 500 ms | 5 秒后仍未返回 | 502 ms 返回 `false` |
| `WaitAsync(CancellationToken)` 500 ms 后取消 | 5 秒后仍未返回 | 507 ms 抛出取消 |
| 同步 `Wait(int)` 500 ms | 516 ms 返回 `false` | 521 ms 返回 `false` |

Npgsql 9.0.4 与 10.0.3 结果相同，用 IPv4 地址连接也一样。生产环境是 Linux，不受影响；但本机开发在 Windows 上，05-07、05-08、05-10 中“等待 `NOTIFY` 或兜底轮询间隔”的循环如果用 `WaitAsync`，在本机**永远等不到兜底轮询**：投递、作业、缓存失效只在收到通知时才动。

### D1 监听循环用后台线程上的同步 `Wait(超时)`（待决，补充 05-07 D8、05-08 第 4 节、05-10 第 4.3 节）

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 专用后台线程 + 同步 `Wait(超时)`** | 每个进程一个监听连接（05-08 已定），在一个长期运行的专用线程上循环 `Wait(兜底间隔)`；收到通知或超时都唤醒相应的循环（如释放信号量），停机时关闭连接结束等待 | Windows、Linux 行为一致，本机开发与生产相同；每个进程只占一个线程 | 一个阻塞的专用线程（不占线程池） |
| B 用 `WaitAsync` | 写法最自然 | 生产（Linux）正常 | 本机 Windows 上兜底轮询失效，开发时看到的行为与生产不同，问题难以察觉 |
| C 用 `WaitAsync`，另加计时器到点关闭并重开监听连接 | — | 两个平台都能兜底 | 频繁重建连接；重建期间可能漏掉通知，要靠兜底轮询补 |

- **建议**：A。
- **理由**：监听只有一个连接、一个循环，专用线程的代价可以忽略；换来两个平台一致的行为。
- **取舍**：监听循环不是 `async` 写法；Npgsql 修复后可以改回（登记实施待办，升级 Npgsql 时复查）。
