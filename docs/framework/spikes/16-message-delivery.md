# 原型 #16：消息投递、清理与失败路径不重复执行

- 状态：结论已得出，成立；没有待决事项（2026-11-06）
- 来源：08 第 4 节原型 #16（阻断）；05-07 第 6.2、7.3、9.2 节的 R02 补充说明；05-07 第 11 节 R02 补充的必测场景
- 原型代码：分支 `spike/16-17-messaging` 的 `spikes/16-17-messaging/`（与原型 #17 共用；一次性代码，不合入主干）
- 环境：Npgsql 10.0.3；PostgreSQL 18（Testcontainers）

## 1. 做法

投递、处理、清理按 05-07 中的 SQL 原样实现（领取、`FOR SHARE` 复核、带条件的标记与失败记录、保留契约）。每个场景用多个连接**按确定的顺序**交错执行（不靠计时碰运气），并带一个按 R02 之前写法的对照组，确认问题真实存在、修订确实解决了它。业务是否重复执行，用订阅方的“效果表”中该消息的行数判断。

## 2. 结论

**成立。** R02 对 05-07 的三处修订在 PG 18 上都按设计工作；对照组全部出现重复执行。

| 场景 | R02 修订后 | 原写法（对照组） |
|---|---|---|
| 投递者 A 读出载荷后暂停 → 租约到期，B 接管并投递、处理 → 按保留期清理来源行与去重凭证 → A 恢复后写入 Inbox | `FOR SHARE` 复核不到本次领取的行，回滚，不写入；**执行 1 次** | 去重凭证已删，写入成功；**执行 2 次** |
| A 复核通过、Inbox 写入尚未提交时租约到期 | 接管领取（`SKIP LOCKED`）跳过该行；B 的“标记已投递”、清理的删除都要等锁（实测在 500 毫秒锁等待上限内超时）；A 提交后 B 才能继续 | — |
| 消息写入 quotation 成功、写入 orders 失败进入死信 → 清理 → 运维重试死信 | 来源行还在，quotation 的已处理行不被清理；重试时 quotation 的写入被唯一约束挡住，orders 正常处理；**各执行 1 次** | 已处理行按保留期被删；重试后 quotation **执行 2 次** |
| 处理事务已提交，处理程序没有收到确认、转入失败路径 | 带条件的失败记录影响 0 行，重新读取为“已处理”，不改状态；**执行 1 次** | 无条件的失败记录把“已处理”改回“待处理”；**执行 2 次** |

共 7 项测试（含 3 个对照组），全部通过，连续运行 3 次结果相同。

## 3. 说明

- “确认丢失”是模拟的：处理事务正常提交后，直接调用失败路径。这个场景的正确性只取决于数据库中的行状态，与连接怎样断开无关。
- `FOR SHARE` 复核锁住来源行的时间就是写入一个订阅方 Inbox 的短事务，期间其他实例对这一行的接管、标记、清理都会等待或跳过；不影响其他消息。
- 测试中缩短了保留期（直接以 0 清理），对应 05-07 第 11 节“涉及保留期的测试缩短保留期即可”。
