> 目的：把旧项目盘点（01）和已确认的 ADR 汇总成一份框架需求清单，作为技术选型（03）和架构设计（04）的输入。
> 范围：只列底层框架能力，不含具体业务功能。
> 标注：`待决` = 需要负责人拍板；`待确认` = 需要核实的事实；`假设` = 未验证的推断。
> 状态：已确认（2026-11-04）。本文写于 05～08 之前，确认时已按其后的决定更新各条的依据；仍为待决 / 待确认的事项见第 8 节与 00-README。

## 0. 结论速览

- 共整理功能需求 **16 类 / 119 条**、非功能需求 **6 类**。绝大部分已有 ADR 作为依据，本文只做汇总和编号，不重复论证。
- 旧系统中存在、但不属于框架现阶段范围的能力（Excel、Word/PDF、工作日日历、搜索等），列入第 6 节“按需能力清单”：现在不设计、不选型，只记录必须遵守的约束。
- 框架范围内的两项新决策已确认：业务编号采用计数表 + 行锁（ADR-0024），不预留多租户（ADR-0023）。
- 非功能需求中的性能和容量指标，旧系统没有任何基线数据，需要先核实用户量和数据量（`待确认`）。

## 1. 范围

### 1.1 什么算框架能力

一项能力进入框架设计，需要同时满足：

1. **横切**：每个模块都会用到，不是某几个业务才需要；
2. **事后补成本高**：影响表结构、接口契约或请求管道，晚了要回头改所有模块；
3. **与业务无关**：规则内容和数据不由业务决定。

不满足的能力：
- 属于业务的（如工作日日历的数据与维护），归业务模块；
- 只是部分模块需要的通用能力（如 Excel 导出），列入第 6 节按需能力清单，等第一个真实使用场景出现时再设计和选型。

### 1.2 包含与不包含

| 包含 | 不包含 |
|---|---|
| 模块化结构、领域与应用基础构件 | 具体业务模块的划分与业务规则 |
| 认证、授权、审计 | 审批流程、业务状态的具体定义 |
| 数据访问、事务、并发、迁移 | 旧数据迁移、新旧系统并行过渡（后续单独处理） |
| 接口约定、错误处理 | 前端框架设计（只列与后端契约相关的部分） |
| 模块间通信、后台任务、通知、文件 | 具体报表口径 |
| 可观测性、配置、缓存、部署 | 按需能力的选型（见第 6 节） |

## 3. 功能需求

每类先用一句话说明“旧项目怎么做的 → 新框架怎么做”，再列需求条目。

## 5. 框架范围内的决策

### 5.1 业务编号的生成方式（已确认：计数表 + 行锁，见 ADR-0024）

ADR-0009 已确定编号与主键分离、由框架提供编号服务，但未定实现方式。旧系统用“查最大值 + 1”加进程内锁，多实例会重号。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **计数表 + 行锁** | 每个模块 schema 一张计数表，按“规则 + 周期”一行，在业务事务内 `UPDATE … RETURNING` 取号 | 与业务同一事务，回滚不消耗号码、不跳号；按年 / 月重置简单 | 同一规则的并发取号在该行上串行（锁持有到事务结束） |
| PG 序列 | 每个规则一个 sequence | 并发性能最好 | 事务回滚也会消耗号码（跳号）；按年重置需要额外管理 |
| 预分配号段 | 每个实例一次领取一段号码 | 高并发 | 跳号、实例重启丢号、编号不按时间顺序 |

- **结论**：计数表 + 行锁，框架提供构件，计数表放在使用它的模块 schema 内（符合 ADR-0006）。
- **理由**：业务编号通常要求连续、可解释（如审计查“为什么缺号”）；单据创建的并发量远达不到行锁成为瓶颈的程度。
- **取舍**：放弃极端高并发下的取号性能；业务事务应保持短小，避免长时间持有编号锁。

### 5.2 多租户（已确认：不预留）

见 ADR-0023。
