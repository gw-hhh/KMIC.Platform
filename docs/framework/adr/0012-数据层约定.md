# ADR-0012 数据层约定

- 状态：已确认
- 日期：2026-11-03

## 背景

旧系统（SQL Server）的问题：
- 日期大量存为字符串；
- 软删除字段有多种写法（`DeleteMark`、`IsDel`、`IsDeleted`），由业务代码手写过滤；
- 没有乐观并发控制；
- 表结构靠手工 SQL 脚本维护，没有迁移工具。

新系统使用 PostgreSQL + EF Core，模块完全隔离，每个模块独占一个 schema（ADR-0006）。

## 决策

### 1. 命名风格：保留大驼峰

- 表名、列名、schema 名与 C# 命名一致，如 `"Quotation"."QuotationItem"."CreatedAt"`，不做名称转换。
- 约束和索引沿用 EF Core 默认命名：`PK_`、`FK_`、`IX_`。
- 备选方案“小写下划线”的优点是 PG 中无需引号、符合 PG 生态习惯。最终选择大驼峰，换来 C# 与数据库名称完全一致、查询结果与代码对照直观。
- 由此带来的约束：
  - PG 会把不加引号的标识符转成小写，**所有手写 SQL（Dapper、迁移中的 SQL、报表、运维脚本）中的表名、列名、schema 名都必须加双引号**，否则报“对象不存在”；
  - 标识符大小写敏感，`"Quotation"` 与 `quotation` 是不同对象；
  - 手写 SQL 纳入代码评审检查项。

### 2. 时间存储

| 类型 | C# | PG | 例子 |
|---|---|---|---|
| 时刻 | `DateTimeOffset`（偏移为 0） | `timestamptz` | 创建、提交、审批时间 |
| 纯日期 | `DateOnly` | `date` | 交货日期、签订日期 |
| 纯时间 | `TimeOnly` | `time` | 每日提醒时间 |

- 时刻统一按 UTC 存储；接口使用带时区的 ISO 8601 格式，前端转换为本地时间显示。
- 业务时区配置为 `Asia/Shanghai`。按天、按月切分的逻辑统一使用框架提供的方法计算，报表 SQL 按天分组时必须显式转换时区。
- 禁止用字符串存储日期和时间。
- 容器镜像必须包含时区数据（`待确认` 镜像选择）。

### 3. 软删除

- 区分三个概念：
  - **删除**：框架能力，可恢复；
  - **停用**：业务状态，由领域模型定义；
  - **归档**：业务能力，按需设计。
- 需要可恢复删除的聚合实现 `ISoftDeletable`，框架负责：
  - 把删除改写为标记删除，并记录删除人和删除时间；
  - 用全局查询过滤器排除已删除数据；
  - 回收站通过显式绕过过滤器实现。
- 唯一约束使用 PG 部分唯一索引，只对未删除数据生效，由框架映射约定自动生成。
- 已删除或停用的数据被引用时：历史记录保留原值，读取时标记 `[已删除]` / `[已禁用]`，且不可被新数据选用。
- 手写 SQL 不受全局过滤器保护，必须自行加条件。
- **核心业务优先记录事实，而不是删除**：已产生业务影响的数据（如已提交的单据、已发生的回款）通过“取消、作废、撤销、冲销”等新事实表达，原记录保留。软删除只用于确有恢复价值的对象，物理删除必须有明确的生命周期、权限和审计。

### 4. 乐观并发与版本

- 聚合根使用应用管理的并发版本列 `ConcurrencyVersion`（bigint）。聚合内任何实体发生变化，保存时框架都会递增聚合根的版本号，更新条件同时匹配主键和期望版本，影响零行即为冲突。
- 不使用 PG 系统列 `xmin`：它只反映单行变化，检测不到子表的变更，也不适合作为接口契约。
- 版本号暴露给前端：详情接口返回，修改时带回；冲突时返回 409，并在错误响应中带上最新版本号。
- **并发版本与业务版本严格分开**：
  - `ConcurrencyVersion`：防止多人编辑互相覆盖，每次保存都递增；
  - `Revision`：业务版本（如报价的 V1、V2），只在业务上产生新版本时递增。保存草稿会改变并发版本，但不一定产生新的业务版本。
- **共享额度**（可发货量、可排产量、可冲销金额等多个对象争抢的数量）不能只靠版本号保护，必须在事务内重新计算，并通过原子条件更新、必要的锁或数据库约束防止超量。

### 4.1 金额与精度

- C# 使用 `decimal`，PG 使用明确精度的 `numeric(p,s)`，禁止用浮点类型表示金额、数量、税率。
- 单价、数量、税率、折扣的精度，以及舍入方式和顺序，在框架中统一定义（具体数值随业务确认）。

### 5. 数据库迁移

- 每个模块一套 EF Core Migrations，迁移历史表放在模块自己的 schema 中。
- 开发环境：启动时自动应用迁移。
- 生产环境：
  - 禁止在应用启动时自动迁移；
  - CI 生成幂等 SQL 脚本或迁移包，经审查后，由独立的迁移步骤在应用启动前执行。
- 只向前迁移，回滚依靠备份和新的修正迁移。
- 破坏性变更按“扩展 → 迁移 → 收缩”分步发布，保证新旧版本应用可以共存。
- 视图、函数等复杂对象在迁移中手写 SQL（同样遵守大驼峰加引号的规则）。

### 6. 查询侧技术

- 只使用 EF Core，不引入 Dapper：
  - 简单查询用 LINQ 投影；
  - 复杂查询用 EF 原生 SQL 查询，映射到任意结果类型。
- 选择理由：
  - 一套技术，日志、追踪、慢查询、软删除过滤等拦截器统一生效；
  - LINQ 不需要手写大驼峰引号；
  - 无跟踪投影查询与 Dapper 的性能差距通常很小。
- 极个别性能要求极端的场景，经评审后可以在单个模块的基础设施层局部使用 Dapper，但不作为框架标准。
- 查询约定：
  - 查询专用 DbContext 默认不跟踪实体；
  - 查询直接投影为 DTO，不返回领域实体；
  - 查询侧不经过仓储，处理器直接使用查询 DbContext。

## 影响

框架需要提供：
- 时区换算工具；
- 软删除拦截器、查询过滤器、部分唯一索引约定；
- 聚合版本递增拦截器；
- 迁移执行程序与 CI 脚本生成流程。

## 补充说明（2026-11-04，随 05-13 确认）

- 业务时区工具为应用层注入的 `IBusinessCalendar`（`Today`、`DateOf`、`DayRange`、`Range`、`MonthRange`），领域层只接收已换算的日期或 UTC 区间（05-13 D3）。
- 时刻区间一律半开 `[Start, EndExclusive)`；按日期筛选时刻列先换算为 UTC 区间，`WHERE` 中不转换列；按天分组用 `KmicFunctions.ToBusinessDate`，时区作为参数（05-13 第 3.4、3.5 节）。
- “到某天为止”的截止类字段用 `DateOnly`，不存为 23:59:59 的时刻（05-13 第 3.2 节）。
- 前端统一按业务时区显示时刻，`me` 返回 `businessTimeZone`（05-13 D4）。

## 补充说明（2026-11-04，随 R01 M1 确认）

- 表、列与人工建立的索引必须有中文数据库注释，EF 映射（`HasComment`）是唯一来源；框架表与框架列由约定统一注释；缺失时模型校验失败；CI 从模型生成数据字典。详见 05-03 第 3.9 节。
