# ADR-0029 迁移账号与运行账号分离

- 状态：已确认；之后的修订见文末“修订记录”
- 日期：2026-11-03

## 背景

旧系统数据库凭据明文写在配置中，应用账号拥有完整权限。新系统每个模块一个 schema（ADR-0006），需要确定数据库账号的划分方式。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **迁移账号与运行账号分离，运行账号所有模块共用** | 应用被攻破时无法改表结构；只有一个连接池 | 跨 schema 访问在数据库层面不拦截 |
| 在此基础上每个模块一个运行账号 | 隔离在数据库层面也被强制 | 连接池数量 = 实例数 × 模块数，可能超出 PG 连接上限，需要引入连接池中间件；密钥数量成倍增加 |

## 决策

1. **迁移账号**：拥有各模块 schema 的 DDL 权限，只供 `Kmic.MigrationRunner` 使用；也用于其维护命令——按保留期分批删除只追加表的过期数据（05-09 第 7.3 节）。
2. **运行账号**：只有 DML 权限（`SELECT` / `INSERT` / `UPDATE` / `DELETE`），所有模块共用；不能创建、修改、删除表。只追加表（`AuditLog`、`SecurityEvent`、各 `{聚合}StateHistory`）对运行账号撤销 `UPDATE` / `DELETE`，由迁移约定自动生成（05-09 D7）。
3. **运维账号**：`Kmic.Operator` 使用单独账号，权限按运维命令所需授予。
4. 三个账号的凭据都按密钥管理（ADR-0016），不进代码和镜像。
5. 跨 schema 访问的拦截依靠：项目引用、架构测试检查 EF 模型、代码评审检查手写 SQL（ADR-0008）。
6. 以后拆分服务或安全审计提出要求时，升级为每个模块一个运行账号。

## 影响

- 迁移脚本需要在授权语句中为运行账号授予新建表的 DML 权限，由框架的迁移约定统一处理。
