# ADR-0018 审计事件与业务历史

- 状态：已确认；之后的修订见文末“修订记录”
- 日期：2026-11-03

## 背景

旧系统的操作日志分散在三个库的多张 `*_Log` 表中，结构各不相同；字段级变更没有统一记录；“谁做了什么操作”和“单据为什么变成这个状态”混在一起，事后难以追溯。

## 决策

### 1. 三类记录分开

| 类型 | 回答的问题 | 写入方式 |
|---|---|---|
| 审计字段 | 这条数据由谁、何时创建和修改 | EF 影子属性，拦截器自动写入（见 ADR-0011） |
| 审计事件 | 谁在什么时候执行了什么系统操作 | 关键写操作与业务写入**同一事务**提交：随业务事务写入 Outbox，汇总到 Operations 的 `AuditLog`（05-09 D3） |
| 业务历史 | 业务对象为什么发生了这次状态变化 | 状态变化时由框架写入，与业务写入同一事务 |

### 2. 业务历史

- 有状态流转的聚合，主表保存当前状态，历史表记录每一次变化：原状态、新状态、动作、原因、操作人、操作人当时的角色、发生时间、业务版本（Revision）、追踪 ID。
- 由状态机构件（ADR-0011）在状态转换时自动产生，业务代码只需提供原因等业务信息。

### 3. 审计事件

- 记录操作人、实际操作人（模拟身份时）、当前角色、动作、目标资源、结果、追踪 ID、时间；字段级变更记录变更前后的值，敏感字段只记录“已修改”。
- 需要审计的命令通过标记声明，由管道统一写入：每个命令必须声明 `[Audited]` 或 `[NotAudited("原因")]`；敏感权限点、物理删除、授权配置、幂等类命令强制审计；只审计成功的命令；敏感查询用 `[AuditedRead]`（05-09 D1、D4、D5）。
- 字段级变更记录全部变更字段，在 EF 映射中配置遮盖 / 隐藏 / 排除，命名规则兜底（05-09 D2）。
- 审计事件不在模块中建表，Operations `AuditLog` 是唯一长期存储（05-09 D3）。

### 4. 安全事件

- 登录失败、认证失败、授权拒绝等安全事件走**独立通道**写入，不随业务事务回滚而丢失：经内存有界队列批量写入 Identity，队列满时丢弃并告警（05-09 D6）。
- 拒绝时对外按安全策略返回（如 404），审计中记录真实原因。

### 5. 保留与清理

- 审计事件、业务历史、幂等记录、Outbox 记录不随普通数据清理任务删除，保留期限由运维策略单独规定（`待确认`）。
- 审计、安全事件、业务历史表对运行账号只授予 `INSERT` / `SELECT`，过期数据由 MigrationRunner 删除；暂不分区，触发条件登记在延后事项表（05-09 D7、D8）。

## 影响

- 每个有状态的聚合需要一张业务历史表，由模块模板生成。
- 框架需要提供：审计事件写入管道、状态机与业务历史的联动、安全事件独立通道。
