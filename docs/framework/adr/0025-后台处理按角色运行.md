# ADR-0025 后台处理按角色运行

- 状态：已确认；之后的修订见文末“修订记录”
- 日期：2026-11-03

## 背景

ADR-0021 只规划了一个 Web 宿主 `Kmic.Api`。Outbox 投递、Inbox 处理、Quartz 触发、后台作业需要明确在哪个进程中运行。旧系统的 Hangfire 跑在 Web 进程内，`WorkerCount = CPU × 5`，后台任务与页面请求互相争抢资源。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 同进程，每个实例都跑后台处理 | 最简单 | 大批量处理会抢占 API 的 CPU 和连接池 |
| 独立 Worker 宿主项目和镜像 | 负载彻底隔离 | 多一个宿主，两边的模块注册要保持一致 |
| **同一镜像，按配置分角色** | 默认与同进程一样简单；需要时只改配置即可拆分 | 启动代码需要按角色条件注册；角色配置错误会导致消息积压 |

## 决策

1. 应用只有一个程序、一个镜像，配置项 `Roles` 取值 `Api`、`Worker` 或两者。
   - `Api`：HTTP 端点、健康检查；
   - `Worker`：Outbox 投递、Inbox 处理、Quartz 调度、后台作业执行。
2. 默认两个角色都启用。生产环境可以拆成“只跑 Api”和“只跑 Worker”两组容器。
3. 两个角色使用同一套模块注册（`IModule`），后台处理同样经过中介者管道（ADR-0005）。
4. 启动时校验：`Roles` 不能为空。
5. Outbox / Inbox 积压量和最老消息等待时长必须配置告警，用于发现“没有任何实例在跑 Worker”这类配置错误。
6. **负载隔离落实到连接池**（05-08 D2、05-03 第 2.1 节）：前台（`Origin = Http`）与后台（Inbox、定时任务、后台作业、启动任务）使用不同的数据源，`Application Name` 分别为 `kmic-api` / `kmic-worker`；每个来源再分事务池与读池，共 4 个数据源，各自有连接池上限；Worker 另有一个只供导出主查询使用的流式池（原型 #15 D2）。命令持有事务连接时的嵌套读取一律走读池，从结构上避免连接池自锁（R01 H1，原型 #15 已验证）。
7. 启动任务在两种角色中都执行，用咨询锁 + 内容哈希去重；后台组件在启动任务完成后才开始（05-08 D1、第 3.2 节）。
8. Api 角色中的 Quartz 调度器以待机模式注册，只用于手动触发和修改时间，由 Worker 执行（05-08 第 5.2 节）。

## 影响

- 宿主启动代码按角色条件注册服务。
- 就绪检查按角色区分：只跑 Worker 的实例不接收 HTTP 流量。
