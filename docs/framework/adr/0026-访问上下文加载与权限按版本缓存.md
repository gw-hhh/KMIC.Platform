# ADR-0026 访问上下文加载与权限按版本缓存

- 状态：已确认（2026-11-05 随 R02 加补充说明，已确认）
- 日期：2026-11-03
- 细化：ADR-0001 第 5、8 条，ADR-0015 第 5 节，ADR-0016 第 2 节

## 背景

ADR-0001 和 ADR-0016 要求：每个请求从数据库一次查询加载会话与访问上下文，不跨请求缓存，保证“禁用、改权限立即生效”。但当前角色的权限点集合可能有几百条，每个请求都完整读取一遍并不必要。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 全部每次查库 | 最直接 | 每个请求重复读取大量权限数据 |
| **状态每次查库，权限点集合按版本缓存** | 缓存键包含授权版本，版本一变就换键，不可能读到过期权限 | 必须保证“权限变化一定递增版本” |

## 决策

1. **加载时机**：在 JWT 验证通过的回调中加载访问上下文。会话失效、用户禁用即为认证失败，返回 401。
2. **状态部分每次查库**：一次查询读取会话状态、用户状态、当前角色及其状态和授权版本、“用户-角色”授予（含绝对数据范围）、用户所属组织单元、模拟身份信息。这些数据都在 Identity 模块的 schema 中（ADR-0027、ADR-0031）。
3. **权限点集合按版本缓存**：缓存键为 `Identity:RolePermissions:{角色ID}:{授权版本}`。同一个版本对应的权限集合永远不变，因此可以缓存，不违背“立即生效”。
4. **版本递增由框架统一保证**：角色权限的变更、角色停用只能经过 Identity 模块的统一写入路径，该路径在同一事务中递增授权版本。由集成测试覆盖。
5. **数据范围**在请求内首次需要时计算一次，请求内缓存，不跨请求。计算结果是结构化条件，由 EF 命名过滤器转为参数化 SQL，不拼接字符串、不使用 `like`。

## 影响

- ADR-0016 中“会话状态和授权上下文不跨请求缓存”的含义明确为：**会变化的状态**不跨请求缓存；**按版本不可变的内容**可以缓存。
- 授权版本成为必须守住的不变量，违反时会读到旧权限。

## 补充说明（2026-11-05，随 R02 确认）

R02-4、R02-5 的复核发现：版本键只保证“同一个键对应的内容不变”，不保证“请求读到的状态与内容属于同一个版本”。第 2、3 条修订如下，其余不变：

| 原决策 | 修订 |
|---|---|
| 第 2 条：状态查询读取当前角色及其状态 | 状态查询只读角色的**版本号**（以及组织树版本号）；角色的状态、是否受保护、默认范围、范围覆盖移入按版本缓存的快照 |
| 第 3 条：权限点集合按版本缓存，键 `Identity:RolePermissions:{角色ID}:{授权版本}` | 缓存完整的角色授权快照（状态、是否受保护、权限点、默认范围、范围覆盖），键改为 `Identity:RoleSnapshot:{角色ID}:{授权版本}`（05-05 第 4.3 节补充说明） |
| （新增）未命中时怎样读取 | 在只读的可重复读事务中重新执行状态查询并读取内容，本请求全部使用这次的结果；缓存只由这条路径写入；访问上下文加载固定读主实例（05-04 第 6.1 节补充说明） |
| （新增）撤权的生效边界 | 撤权提交后开始的请求立即生效；正在进行的请求按开始时的授权执行完，上限为请求超时；Identity 的授权管理命令提交前在同一事务中对操作者的会话、用户、授予、角色加共享锁重查（05-05 第 4.6 节） |
| （新增）版本号不回退的前提 | 版本键缓存假设版本号只增不减、不会重复使用。数据库按时间点恢复会让版本号回到恢复点，恢复后可能出现“同一个键、不同内容”。因此恢复后、切换生产流量前，必须重启全部应用实例（清空进程内缓存）；启用 Redis 二级缓存后还要清空 Redis（09 第 11.2 节补充说明、00-README 延后事项“Redis 二级缓存”） |
