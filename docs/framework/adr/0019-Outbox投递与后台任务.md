# ADR-0019 Outbox 投递与后台任务

- 状态：已确认
- 日期：2026-11-03

## 背景

ADR-0007 确定了“集成事件和对外副作用写入 Outbox，由后台投递”。

本决策细化两件事：
- 多实例运行时，怎么做到消息不重复处理、不丢失、失败可知；
- 定时任务和长任务的实现方式。

旧系统使用 Hangfire。它把方法调用序列化后存库，面板使用固定账号密码，任务没有统一的执行记录和告警。

## 决策

### 1. Outbox：自建

- 不引入 Wolverine、MassTransit 等框架：
  - 它们会和已选的中介者、模块独立 schema、Inbox 设计重叠；
  - MassTransit v9 起为商业许可。
- 每个模块的 Outbox 表放在本模块 schema 中，由统一的投递程序处理。

| 环节 | 做法 |
|---|---|
| 领取 | 短事务内用 `FOR UPDATE SKIP LOCKED` 批量领取，标记为“处理中”，写入租约到期时间和领取令牌 |
| 处理 | 在数据库事务之外执行 |
| 完成 | 回写结果时校验领取令牌，租约过期后被他人重新领取的消息，原实例不能覆盖结果 |
| 重试 | 指数退避加随机抖动，有最大重试次数 |
| 最终失败 | 进入死信状态，触发告警；管理界面可查看并人工重试 |
| 唤醒 | 默认定时轮询；可选用 PG `LISTEN/NOTIFY` 在写入后立即唤醒 |
| 顺序 | 默认不保证全局顺序；需要顺序时按聚合 ID 串行 |
| 消费者 | 必须幂等（配合 Inbox） |
| 预算 | 单条载荷大小、单批条数有上限 |
| 清理 | 成功消息保留一段时间后清理，期限`待确认` |
| 监控 | 积压数量、最老消息等待时长、失败数量 |

### 2. 任务分类

| 类型 | 例子 | 实现 |
|---|---|---|
| 事件驱动 | 状态变化后发通知、同步读模型 | Outbox |
| 定时任务 | 每日提醒、夜间同步 | Quartz.NET 触发 |
| 用户发起的长任务 | 大数据量导出、批量导入 | 后台作业构件 |

### 3. 定时任务：Quartz.NET

- Quartz.NET 只负责触发，使用数据库集群模式，多实例下同一任务只执行一次。
- 触发后发送中介者命令执行任务，与普通请求走同一条管道，以系统身份执行，具备日志、授权、事务、审计。
- 任务执行记录（开始、结束、耗时、处理条数、结果、错误）写入框架的任务记录表。
- 管理页面由框架提供，复用系统登录和权限点，不使用固定账号密码。
- 每个任务有独立的开关和执行时间配置，配置错过触发时的补偿策略。

### 4. 后台作业（长任务）

- 记录作业状态、进度和结果，前端可以查询进度。
- 完成后发送站内通知，结果文件存入附件存储（见 ADR-0020）。
- 作业有自己的生命周期和取消机制，不沿用已结束的 HTTP 请求。

## 备选方案

| 方案 | 不采用的原因 |
|---|---|
| Hangfire | 序列化方法调用，改类名或参数后已排队的任务会失败 |
| 自建调度器 | Cron 解析、集群、错过触发的补偿都要重做，没有必要 |
| 现成的 Outbox 框架 | 见第 1 节 |

## 影响

- Outbox 的领取令牌、租约、死信、人工重试需要充分测试：多实例并发、进程崩溃、租约过期。
- 需要自建任务管理和死信管理页面。
