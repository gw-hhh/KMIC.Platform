# ADR-0015 授权模型：五层授权

- 状态：已确认
- 日期：2026-11-03

## 背景

旧系统：
- 功能权限 = 当前角色的菜单权限 ∪ 用户个人授权，按钮权限 ID 以数字硬编码在代码中；
- 数据范围散落在约 170 处手写条件中，维度包括本人、上级链、大区、行业、额外授权等；
- 部分判断用 `like '%ID%'`，存在误匹配。

单一的角色权限无法表达“销售可以编辑自己的草稿报价，但不能编辑他人的报价，也不能编辑已确认的报价”这类真实规则。

## 备选方案

| 方案 | 说明 |
|---|---|
| 纯 RBAC | 只回答“有没有这项功能”，不足以表达数据和资源规则 |
| ABAC（属性 / 策略） | 规则有明确名称、版本和测试，并记录判定依据时，同样可以解释和审计；难点在属性来源和规则组合 |
| ReBAC（关系授权） | 关注用户与对象之间的关系。负责人、被指派人、协作者等关系可以先存在业务数据中，不必然需要 OpenFGA 等独立服务 |
| **五层组合模型** | 角色管功能资格，数据范围限制可见集合，资源策略处理具体关系，领域规则控制状态变化，并发条件保证依据有效 |

## 决策

### 1. 五层授权

每个操作必须依次通过五层检查，每层归属明确、可单独测试、拒绝原因可解释：

| 顺序 | 回答的问题 | 机制 | 执行位置 | 拒绝时 |
|---|---|---|---|---|
| 1 | 这个身份有资格做这件事吗 | RBAC 功能权限 | 管道授权行为 | 403 |
| 2 | 这条数据在可见范围内吗 | 数据范围（DataScope） | 查询过滤器 / 加载聚合时 | 404（不泄露数据是否存在，审计记录真实原因） |
| 3 | 这个人和这条数据的关系允许这个动作吗 | 资源策略（ResourcePolicy） | 处理器加载聚合之后 | 403 |
| 4 | 这条数据当前的状态允许这个动作吗 | 领域规则 / 状态机 | 聚合的业务方法 | 422 / 409 |
| 5 | 操作依据的数据仍然是最新的吗 | 并发版本、规则签名等前置条件 | 保存时 | 409 |

- 内部统一使用稳定的拒绝原因码：`MissingPermission`、`OutOfDataScope`、`ResourceDenied`、`InvalidState`、`AssignmentMismatch`、`VersionConflict`、`BusinessRuleViolation`，用于日志、测试和前端映射。
- **列表、详情、统计、导出、下拉选项共用同一套授权基础**，禁止出现“列表只能看自己的，导出却能拿到全部”。
- 查询顺序固定为：数据源 → 授权范围 → 资源可见性 → 业务筛选 → 排序 → 分页 / 聚合。禁止先查全量再由前端过滤。
- 候选人员（如评审人候选列表）同样经过授权计算，提交时再次校验，不信任前端传回的候选结果。

### 2. 功能权限（第 1 层）

- 采用纯 RBAC，**不支持给用户直接授权**。
- 权限点由各模块在代码中声明，格式为 `模块.资源.动作`，启动时自动同步到数据库，供角色管理界面使用。代码中不出现数字权限 ID，禁止按角色名称判断。
- 角色及“角色-权限”关系存储在数据库，由管理员维护。
- 用户可以拥有多个角色，但一个会话只激活一个当前角色；有效权限只来自当前角色，不合并其他角色。
- 权限声明在命令和查询上，由管道统一检查（见 ADR-0011）。

### 3. 数据范围（第 2 层）

- 聚合通过接口声明归属，例如 `IHasOwner`（所属人）、`IHasOrgUnit`（所属组织）。每个模块必须明确归属的业务含义，不假设所有资源都有所属人。
- **相对范围配置在角色上**：本人 / 本组织 / 本组织及下级 / 全部。同一个角色按每个用户自己的组织位置计算。
- **绝对范围配置在“用户-角色”授予关系上**：例如授予张三“销售”角色时注明“范围：华东”。不为不同区域建立不同角色。
- 框架在查询 DbContext 上通过 EF 命名全局过滤器自动套用数据范围，绕过时必须按名称显式关闭；命令侧加载聚合时同样校验。
- 范围维度可以扩展：框架定义扩展点，新维度（如行业）作为插件注册。
- 组织层级由框架定义抽象接口，实现位于 Identity 平台模块（修订：见 ADR-0031）。
- 提供诊断能力：可以查看某用户在某类资源上的数据范围及其计算来源。

### 4. 资源策略（第 3 层）

- 框架提供资源策略构件，接口形式为“给定当前访问上下文、资源和动作，返回允许或拒绝及原因”。业务代码不直接查询指派表，以便以后替换为关系授权服务。
- 负责人、被指派人、协作者等关系先存在业务数据中，不引入 OpenFGA。出现大量跨模块共享、层级继承、委托授权和统一关系查询需求时，再评估。
- 每类资源一组小而明确的策略，禁止一个包含所有模块判断的“全局数据权限服务”。
- 敏感资源有特殊默认规则，例如私有消息只允许收件人读取，“全部”数据范围也不能读取他人的私有消息正文。

**资源策略与领域规则的划分标准**：

| 归属 | 判断标准 | 例子 |
|---|---|---|
| 资源策略（403） | 访问控制：谁可以碰这条数据 | 只有被指派人能审批；只有负责人能编辑 |
| 领域规则（422） | 业务流程规则：即使没有权限系统，业务上也必须成立 | 提交人不能审批自己的单据；金额超过阈值必须二级审批 |

### 5. 授权版本

- 角色的权限变化、角色被停用时，递增该角色的授权版本。每个请求从数据库加载当前访问上下文时比较版本（会话与授权不跨请求缓存，见 ADR-0016）。
- **权限内容变化**：用新权限处理本次请求，并在响应头中返回新的授权版本号；前端发现版本变化后，在后台重新拉取权限和菜单，刷新界面。
- **当前角色被停用或被收回**：拒绝请求，前端引导用户重新选择角色。

### 6. 前端按钮与允许的操作

- 详情类接口返回 `allowedActions`（如 `["edit", "submit"]`），由后端使用同一套五层检查计算。
- 前端只按 `allowedActions` 显示或禁用按钮，不自行判断权限；前端权限只服务于体验，后端每次都要完整校验。

### 7. 防止角色膨胀

- 岗位能做什么 → 角色；
- 能看哪个区域、哪些客户 → 数据范围；
- 这一单由谁处理 → 资源关系（指派、协作）；
- 不为某个人、某个区域或某一单建立专门的角色。

## 影响

- 授权层次增多，开发人员需要按上表判断一项检查属于哪一层，编码规范中给出示例。
- 手写 SQL 不受全局过滤器保护，必须调用框架提供的数据范围条件生成方法。
- 每个资源的测试至少覆盖：各范围等级、本人与他人、跨区域、角色切换、禁用用户，以及列表、详情、导出、选项的一致性。
- 框架需要提供：权限点声明与同步、授权管道行为、数据范围过滤器与扩展点、资源策略构件、授权版本、`allowedActions` 计算支持、诊断接口。

## 补充说明（2026-11-04，随 05-05 确认）

- **范围组合语义**：数据范围等级（本人 / 本组织 / 本组织及下级 / 全部）是累加的；角色上有默认等级，可按“范围对象”单独覆盖。授予上的绝对范围（锚点组织单元）**代替**用户所属组织作为计算起点，不与相对范围取并集。
- **菜单**：菜单由前端路由定义并声明所需权限点，后端不保存菜单；按钮由 `allowedActions` 决定。
- **授权版本**：即角色聚合的并发版本，由数据层拦截器保证“有变化必递增”。
- **关系可见**：是否让审批人、协作者看到范围外数据由业务模块决定；用时必须写进同一个数据范围过滤器。扩展维度的组合方式延后到第一个维度出现时决定。
