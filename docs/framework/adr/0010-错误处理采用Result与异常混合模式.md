# ADR-0010 错误处理采用 Result 与异常混合模式

- 状态：已确认
- 日期：2026-11-03

## 背景

旧系统没有错误码体系：
- 页面异常直接 `alert` 给用户；
- ashx 返回 `{"code":1,"msg":"..."}`，前端只能靠匹配提示文字判断；
- 业务失败和系统故障不加区分。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 全部用异常 | 代码最少 | 方法签名看不出会失败；用异常控制业务流程是反模式；高频业务失败有性能开销 |
| 全部用 Result | 失败显式 | 意外错误也包装成 Result 会很啰嗦，最终仍离不开异常 |
| **混合模式** | 预期失败显式且可枚举，意外错误统一兜底 | 代码量比纯异常多；团队需守住两者边界 |

## 决策

1. **两类错误分开处理**：
   - 预期失败（校验失败、不存在、冲突、无权限、违反业务规则）用 `Result` 表达；
   - 意外错误（基础设施故障、程序缺陷）用异常表达。
2. **领域层**：聚合的业务方法违反业务规则时返回 `Result`；只有程序缺陷导致不变量被破坏时才抛异常。
3. **应用层**：所有命令和查询处理器返回 `Result` 或 `Result<T>`。
4. **错误对象** `Error` 包含三项：
   - 错误码，格式为 `模块.错误名`，如 `Quotation.AlreadySubmitted`；
   - 提示信息；
   - 错误类型：校验失败 / 不存在 / 冲突 / 无权限 / 业务规则。
5. **错误目录**：每个模块把全部业务错误集中定义在一处，业务代码中不允许临时创建错误。
6. **接口层**：框架统一把 `Result` 转换为 HTTP 响应。失败时按错误类型映射状态码，并返回 ProblemDetails，扩展字段中带错误码。端点内不写转换逻辑。
7. **全局异常处理**：记录完整日志，返回 500 和追踪 ID，不向用户暴露堆栈。
8. **自建 Result 类型**，不使用第三方库，以便与错误码体系和 ProblemDetails 映射完全贴合，并避免第三方的版本或许可风险。

## 影响

- 错误码对前端稳定、可枚举，以后做多语言可按错误码翻译。
- 编码规范要明确：业务失败不得抛异常，系统故障不得包装成 Result。
- 能用分析器检查的规则，由分析器检查。
