# ADR-0028 集成事件两阶段投递

- 状态：已确认；之后的修订见文末“修订记录”
- 日期：2026-11-03
- 细化：ADR-0007、ADR-0019

## 背景

一个集成事件可能有多个订阅方。某个订阅方处理失败时，不能影响其他订阅方，也不能导致已经成功的订阅方重复处理。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 单阶段：投递程序依次调用每个订阅方，Outbox 中记录各订阅方状态 | 链路短 | 发布方的 Outbox 要知道订阅方，耦合；慢订阅方拖住整条消息 |
| **两阶段：Outbox → 各订阅方 Inbox** | 订阅方之间完全隔离；“处理 + 标记”在订阅方 schema 中同一事务完成；拆成服务后结构不变 | 多一次落库，延迟略增，行数增加 |

## 决策

1. **第一阶段（投递）**：投递程序以 `SKIP LOCKED` + 租约 + 领取令牌领取 Outbox 消息，按事件 ID 幂等写入每个订阅模块的 Inbox，然后校验领取令牌并标记 Outbox 已投递。
2. **第二阶段（处理）**：各模块的 Inbox 处理程序以同样的领取机制领取消息，经中介者管道以系统身份执行处理器，处理结果与“标记已处理”在订阅方自己的 schema 中同一事务提交。事件映射为订阅方模块的 `[SystemOnly]` 命令，事务行为在提交前校验领取令牌并标记 Inbox 已处理；Inbox 一行 = 一条消息 × 一个订阅（05-07 D9、第 7.1 节）。
3. **重试与死信**按订阅方独立：退避重试、最大次数、死信、人工重试（ADR-0019）都作用在 Inbox 上。Outbox 的重试只针对“写入 Inbox”这一步。失败分类（05-07 D10）：异常与可重试错误（`Unavailable`、`Common.VersionConflict`、`Common.RequestInProgress`）退避重试；其他业务失败与反序列化失败立即进入死信。
4. **订阅关系**由各模块在 `IModule` 中声明，启动时登记到订阅路由表 `"Operations"."MessageRoute"`；投递程序按路由表写 Inbox，Inbox 处理程序只领取本实例认识的订阅。路由只增不自动删，持久状态决定投递，终结订阅是维护窗口中的人工操作（05-07 D7、第 6.3 节）。
5. 投递程序是框架基础设施，向订阅方 Inbox 写入不视为“模块访问其他模块的数据”。
6. Outbox 记录保存发布时的 `traceparent`，处理时以链接方式关联原始请求。
7. 写入后用 PG `LISTEN / NOTIFY` 唤醒投递和处理程序，另有 10 秒兜底轮询（05-07 D8）。
8. **顺序**：默认不保证，读模型按来源版本取最新；订阅可声明 `Ordered()`，按发布方 Outbox 的 `Seq` 同键串行（05-07 D11）。
9. **读模型重建**：从源模块分页快照拉取，按版本 upsert，不依赖事件重放（05-07 D12）。

## 影响

- 清理任务需要同时覆盖 Outbox 和 Inbox。
- 监控指标同时覆盖两段：Outbox 积压（投递慢）和各模块 Inbox 积压（处理慢）。
- 以后改用消息中间件时，第一阶段由中间件替代，Inbox 处理保持不变。
