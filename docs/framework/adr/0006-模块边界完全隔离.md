# ADR-0006 模块边界完全隔离

- 状态：已确认
- 日期：2026-11-03

## 背景

旧系统任何页面都能读写任何表，表之间几乎没有外键，冗余字段靠触发器同步，跨库视图和触发器把多个业务绑死。模块化单体能否长期保持边界、能否拆成微服务，取决于数据边界有多严。

## 备选方案

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| 宽松 | 同一个库，任何模块可读写任何表 | 开发最快 | 迅速退化为旧系统 |
| 写严读宽 | 写只能经过所属模块，读可以访问其他模块的公开视图 | 兼顾灵活 | 跨 schema 查询会阻碍以后拆分 |
| **完全隔离** | 读写都只能访问本模块数据，跨模块只通过 Contracts 和集成事件 | 边界最清晰，拆微服务成本最低 | 跨模块的综合查询需要专门设计读模型，开发量更大 |

## 决策

采用**完全隔离**：

1. 每个模块在 PostgreSQL 中独占一个 schema，有自己的 DbContext。
2. 模块不得读写其他模块的表，SQL 中不得出现跨 schema 引用。
3. 需要其他模块的数据时：
   - **同步**：调用对方 `Contracts` 中的公开接口；
   - **异步**：订阅对方的集成事件，在本模块维护所需数据的副本（读模型）。
4. 一个数据库事务只能修改一个模块的数据。跨模块的一致性通过集成事件实现最终一致。
5. 模块之间不引用对方的实体、DbContext 和内部服务。
6. 跨模块报表、综合查询的实现方式（专用报表模块、读模型等）在架构文档中设计。

## 影响

- 以后把模块拆成独立服务时，数据库可以直接迁出。
- 需要设计跨模块查询的统一做法，避免各模块各写一套。
- 冗余数据（如用户姓名）通过集成事件更新，不再使用数据库触发器。
