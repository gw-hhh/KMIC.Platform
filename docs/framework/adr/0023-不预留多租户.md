# ADR-0023 不预留多租户

- 状态：已确认
- 日期：2026-11-03

## 背景

旧系统没有多租户，单公司使用，组织维度是大区、行业和上下级关系。多租户是结构性决定：一旦预留，每张表、每个索引、每个查询都要多一个维度，事后增加或去掉的代价都很大，所以需要现在明确。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| **不预留** | 没有额外复杂度 | 以后需要支持多公司时，改造成本高 |
| 预留 `TenantId` 列与全局过滤器 | 以后启用成本低 | 每张表、每个索引、每个查询都多一个维度，在没有需求的情况下长期承担这份复杂度 |
| 每个租户一个数据库 | 隔离最强 | 运维成本高，与当前单公司场景不匹配 |

## 决策

**不预留多租户**：

- 表结构、查询过滤器、缓存键、编号规则中都不包含租户维度。
- 组织内的隔离需求（大区、行业、上下级）由数据范围承担（ADR-0015）。

## 理由

- 单公司使用，没有明确的多公司计划；
- 组织内的隔离已经有数据范围机制承担；
- 符合“出现真实需求再扩展”的原则（ADR-0016 第 3 节）。

## 影响

- 以后如果需要支持集团内多家公司，需要单独立项改造。届时优先评估“每公司一套部署”，因为它不需要改动代码。
