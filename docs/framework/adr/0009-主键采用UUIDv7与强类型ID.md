# ADR-0009 主键采用 UUID v7 + 强类型 ID

- 状态：已确认
- 日期：2026-11-03

## 背景

旧系统主键以数据库自增 bigint/int 为主，另有字符串和 GUID 主键，部分表没有主键。业务编号（报价单号等）在代码中按“最大值 + 1”生成，并依赖进程内锁防重。

新系统采用 DDD 与模块完全隔离（ADR-0003、ADR-0006），要求实体创建时就有身份、跨模块和以后拆分服务时标识不冲突，同时避免接口暴露可被顺序猜测的 ID。

## 备选方案

| 方案 | 优点 | 缺点 |
|---|---|---|
| 自增 bigint | 8 字节、索引最好、可读 | 入库后才有 ID；可被猜测；跨模块/跨库会冲突 |
| 随机 GUID（v4） | 程序生成、全局唯一 | 随机写入导致索引分裂，性能差 |
| **UUID v7** | 程序生成、全局唯一、按时间有序、索引友好、不可顺序猜测 | 16 字节；不易读；暴露大致创建时间 |
| 雪花 ID | 8 字节、有序 | 需分配机器号；超出 JS 数字精度 |
| bigint 主键 + GUID 对外（双标识） | 外键更小 | 两套身份，聚合内关联依赖入库顺序；易误用 bigint 暴露 ID；每表多一个索引。主要解决 v4 的性能问题，v7 已解决 |

## 决策

1. 聚合根和实体使用**单一主键 UUID v7**，由程序生成（`Guid.CreateVersion7()`），PostgreSQL 中为 `uuid` 类型。
2. 使用**强类型 ID**（如 `CustomerId`），避免不同实体的 ID 互相误传；EF Core、JSON、路由参数的转换统一由框架提供，具体实现方式在技术选型中确定。
3. **不使用双标识**（bigint + GUID 并存）。
4. **业务编号与主键分离**：给人看的单号作为普通字段加唯一索引，由框架的编号服务生成，规则可调整且不影响关联。
5. **纯关联表**（多对多中间表）使用复合主键。
6. 不以 ID 判断数据先后顺序（同一毫秒内不保证递增），排序使用创建时间字段。

## 影响

- 外键和索引比 bigint 大一倍，在当前数据量级下可接受。单表达到数亿行并有密集关联时，可针对该表单独评估。
- 框架需要提供：强类型 ID 基础设施、编号生成服务。
