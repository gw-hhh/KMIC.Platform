## 2. 规则如何落地

### 2.1 强度阶梯

与 06 第 2.1 节同一原则：**能用更强手段检查的，不靠更弱的手段**。

```mermaid
graph LR
    A[类型检查<br/>vue-tsc 严格模式] --> B[代码检查<br/>ESLint / Stylelint / cspell]
    B --> C[结构测试<br/>Vitest 中检查路由目录、生成代码等]
    C --> D[运行时校验<br/>开发与测试环境的路由目录校验等]
    D --> E[代码评审<br/>第 13 节清单]
```

| 手段 | 适用 | 失败时 |
|---|---|---|
| 类型检查 | 类型、可空、生成的字面量类型（权限点、错误码、动作编码） | CI 失败 |
| 代码检查 | 单个文件内能判断的规则；目录之间的依赖方向（`eslint-plugin-boundaries`） | CI 失败；全部为错误级别，**不使用警告**（ADR-0021 零警告） |
| 结构测试 | 需要看整个应用的规则（路由目录完整性、每个页面都被路由引用、生成代码未被手改） | CI 失败 |
| 运行时校验 | 需要运行时组装结果才能判断的规则（F03 第 4.1 节的路由目录校验） | 开发与测试环境报错；同一套校验也在结构测试中执行 |
| 代码评审 | 语义层面、工具无法判断的规则 | 评审不通过 |

- 每条规则**只登记一次**，登记在第 14 节规则总表中，写明手段与来源。评审清单（第 13 节）只放工具无法检查的条目；某条一旦能用工具检查，就从清单移到总表。
- 优先使用 ESLint、Stylelint 的内置规则与成熟插件；只有它们表达不了时才写自定义规则。

### 2.2 自定义检查规则

自定义 ESLint 规则放在 `web/tools/eslint-plugin-kmic/`，规则名 `kmic/<名称>`（ESLint 规则以名称标识，不用后端 `KMxxxx` 的编号方式）。每条规则用 ESLint 的 `RuleTester` 至少覆盖“触发”与“不触发”各一例。首批自定义规则见第 14.2 节，共 3 条。

### 2.3 D1 规则豁免怎么写

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 不限制 | 块注释 `/* eslint-disable */`、文件级关闭、配置中按路径关闭都可以 | 灵活 | 块级关闭忘记重新打开会扩大范围；理由不留痕；评审时容易漏看 |
| **B 只允许“下一行、指定规则、写明理由”** | 只能写 `// eslint-disable-next-line 规则名 -- 理由`；禁止不指定规则、块级与文件级关闭；没有理由、多余的豁免都报错。Stylelint 同样只允许 `/* stylelint-disable-next-line 规则名 -- 理由 */`；TypeScript 只允许 `// @ts-expect-error 理由`，禁止 `@ts-ignore` | 每个例外都有理由、范围最小、可以全文搜索出清单；规则修好后多余的豁免会被发现 | 写法较长；个别需要整段豁免的地方要逐行写 |
| C 只允许在配置文件中按路径关闭 | 例外集中在配置中 | 例外集中 | 粒度是文件或目录，范围过大；读代码时看不到 |

- **决定（已确认，2026-11-05）**：B。与后端 06 D1 同一做法。配套：
  - `generated/` 目录在配置中整体忽略（生成代码不手改，F03 第 2.1 节），不需要逐行豁免。
  - `eslint.config.js`、`eslint/`、Stylelint 配置、`tsconfig*.json`、`web/tools/eslint-plugin-kmic/`、组件库允许名单（第 5.8 节）列入 `CODEOWNERS`，修改须框架负责人审核。
- **理由**：豁免本身就是需要评审的设计决定；B 让每个例外都带着理由出现在它生效的位置。
- **取舍**：豁免写法略长。

### 3.2 TypeScript 编译选项

| 选项 | 值 | 理由 |
|---|---|---|
| `strict` | `true` | FE-QA-01 |
| `noUncheckedIndexedAccess` | `true` | 按下标、按键取值的结果可能不存在，强制处理 |
| `noImplicitOverride`、`noFallthroughCasesInSwitch` | `true` | 常见错误 |
| `verbatimModuleSyntax` | `true` | 只导入类型时必须写 `import type`，构建时不会留下多余的导入 |
| `erasableSyntaxOnly` | `true` | 禁止 `enum`、`namespace`、构造函数参数属性等需要转换的语法（第 6.3 节） |
| `exactOptionalPropertyTypes` | 不开启 | 与 Vue 属性、组件库类型的兼容性差，收益不抵改造成本 |

### 3.3 格式化

格式只由 Prettier 决定，代码检查不管格式（与后端 06 D2“只用一个格式化工具”同一思路）。

| 项 | 值 |
|---|---|
| 行宽 | 120（与后端建议一致） |
| 引号 | 单引号；模板与 JSX 属性照 Prettier 默认 |
| 分号 | 保留 |
| 尾随逗号 | `all` |
| 缩进 | 2 个空格 |
| 格式检查 | CI 运行 `prettier --check`，不一致即失败；编辑器保存时自动格式化 |

### 3.4 D2 是否使用自动导入

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 不使用，全部显式导入** | 每个文件写明导入了什么 | 依赖关系在文件中可见；目录边界检查（`eslint-plugin-boundaries`）与组件库允许名单（`no-restricted-imports`，第 5.8 节）都基于导入语句，显式导入才能被检查；编辑器会自动补全导入，书写成本低 | 文件开头多几行导入 |
| B 自动导入 Vue API 与组件（`unplugin-auto-import` + `unplugin-vue-components`，Vben 的做法） | 模板中直接写组件、脚本中直接写 `ref` | 文件更短 | 组件与函数的来源不可见；**边界检查与允许名单失效**——自动注册的组件不经过导入语句；全局类型声明文件需要随时重新生成 |
| C 只自动导入 Vue 核心 API，组件仍显式导入 | — | 折中 | 仍有两种写法；收益只是省掉 `import { ref } from 'vue'` |

- **决定（已确认，2026-11-05）**：A。
- **理由**：本系统的分层与适配层（F03 D1、F02 D4）都依赖“导入语句可检查”；自动导入省下的只是编辑器本来就会自动补全的几行。
- **取舍**：文件开头多几行导入。

## 5. 组件写法

### 5.1 D3 组件用什么写法

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 只用单文件组件 + `<script setup lang="ts">`；渲染函数与 TSX 只在 `platform` 中使用** | 业务模块全部用模板；`platform` 中确实需要按配置生成内容的地方（表格单元格渲染器、动态表单项）可以用渲染函数 | 写法只有一种；模板享有编译期优化，eslint-plugin-vue 能检查模板；评审者只需熟悉一种写法 | `platform` 中个别组件写法不同，需要熟悉渲染函数的人维护 |
| B 业务模块也允许 TSX | 复杂渲染逻辑用 TSX | 复杂动态渲染写起来更顺手 | 同一类页面出现两种写法；TSX 中的模板检查规则（`vue/*`）不生效 |
| C 允许选项式 API | `export default { data, methods }` | 熟悉 Vue 2 的人上手快 | 类型推断弱；与组合式函数（页面实例、请求层都是组合式函数）混用别扭 |

- **决定（已确认，2026-11-05）**：A。
- **理由**：300 多个页面的可读性与一致性最重要；业务页面需要的动态渲染（表格列、表单项）由 `KTable`、`KForm` 以配置和插槽提供，页面不需要自己写渲染函数。
- **取舍**：`platform` 的少数组件用渲染函数，维护者要求更高。

### 5.2 单文件组件的结构

| 规则 | 检查 |
|---|---|
| 块的顺序：`<script setup lang="ts">` → `<template>` → `<style scoped lang="scss">` | `vue/block-order` |
| 一个文件一个组件 | `vue/one-component-per-file` |
| `<script setup>` 内的顺序：导入 → `defineProps` / `defineEmits` / `defineModel` → 框架组合式函数（`usePage`、`useCommand` 等）→ 状态 → 计算属性 → 侦听 → 函数 → 生命周期钩子 | 宏的顺序由 `vue/define-macros-order` 检查；其余评审 |
| 页面组件只做装配：查询、命令、表单、表格的组合；超过约 300 行时，把一组相关逻辑提取为同目录的组合式函数（`use-sample-detail.ts`），或拆出子组件 | 评审 |

### 5.3 属性、事件与双向绑定

| 规则 | 说明 |
|---|---|
| 属性 | 只用类型声明：`defineProps<SampleCardProps>()`；默认值用 Vue 3.5 的解构默认值（`const { size = 'default' } = defineProps<…>()`）；解构出的属性传给 `watch` 或组合式函数时写成取值函数 `() => size` |
| 不修改属性 | `vue/no-mutating-props` |
| 事件 | 用带参数名的元组类型：`defineEmits<{ rowSelect: [id: string] }>()` |
| 双向绑定 | 用 `defineModel`，不手写 `modelValue` + `update:modelValue` |
| 模板引用 | 用 `useTemplateRef`（`vue/prefer-use-template-ref`）；`defineExpose` 只在 `platform` 中使用，业务组件之间不通过引用互相调用方法 |

### 5.4 组件之间的通信

| 允许 | 禁止 |
|---|---|
| 属性向下、事件向上；`defineModel` | 事件总线（`mitt` 一类）、全局事件 |
| `platform` 中用带类型的 `InjectionKey` 做 `provide` / `inject` | 业务模块中使用 `provide` / `inject`（页面的状态在页面组件中，子组件经属性取得） |
| 页面之间：路由导航（带参数）、查询失效（F03 第 7.7 节） | `$parent`、`getCurrentInstance()`、跨页面直接调用 |

### 5.5 响应式

| 规则 | 说明 |
|---|---|
| 默认用 `ref` | `reactive` 只用于确实需要整体传递的一组状态，且不解构（`vue/no-ref-object-reactivity-loss`） |
| 大的只读数据用 `shallowRef` | 如导入预览的大量行；接口数据由 TanStack Query 持有，页面不复制一份响应式副本 |
| 计算属性无副作用 | `vue/no-side-effects-in-computed-properties`、`vue/no-async-in-computed-properties` |
| 侦听写明来源 | 用 `watch(来源, …)`；需要随条件重新请求时改变查询键，由 TanStack Query 重新获取，不在侦听中手动发请求 |

### 5.6 生命周期与标签保持（F03 D2 交给本文的规则）

页面组件由 `KeepAlive` 按标签保持（F03 D2），切换标签时页面**失活而不是卸载**。因此：

| 规则 | 说明 | 检查 |
|---|---|---|
| 定时器、轮询、全局事件监听只经 `platform` 的封装注册 | `useActiveInterval`、`useActiveEventListener`：页面失活时自动暂停、激活时恢复、卸载时清除 | 业务模块中直接使用 `setInterval`、`setTimeout`、`window.addEventListener`、`document.addEventListener` 报错（`no-restricted-globals` / `no-restricted-properties`） |
| VueUse 中注册定时器或全局监听的函数（`useIntervalFn`、`useTimeoutFn`、`useEventListener` 等）同样只经 `platform` 封装 | 它们在页面失活时不会暂停 | 业务模块中按函数名限制导入（`no-restricted-imports`） |
| 激活时需要做的事写在 `onActivated` | 如刷新被标记为过期的查询（F03 第 7.7 节，框架已处理常见情况） | 评审 |
| 失活时需要暂停的其他逻辑写在 `onDeactivated` | 第一行的封装覆盖不到的情况（如暂停视频、停止拖动） | 评审 |

### 5.7 模板

| 规则 | 检查 |
|---|---|
| 模板中不写复杂表达式：超过一个运算或调用的，移到计算属性 | 评审 |
| `v-for` 必须带稳定的 `:key`（数据的 ID），不用下标 | `vue/require-v-for-key`、`vue/valid-v-for`；不用下标由评审 |
| 同一元素上不同时用 `v-if` 与 `v-for` | `vue/no-use-v-if-with-v-for` |
| 禁止 `v-html` | `vue/no-v-html`（F03 第 16 节） |
| 不写静态的行内样式 | `vue/no-static-inline-styles`；动态尺寸等确需行内样式的，只能绑定变量 |
| 模板中使用的组件必须已导入 | `vue/no-undef-components`（与 D2 配合） |

### 5.8 组件库的直接使用名单（F03 第 2.1 节交给本文）

业务模块经 `platform/ui`、`platform/table` 使用交互组件（F02 D4 组件适配层）；纯展示与布局组件可以直接从 `antdv-next` 导入。名单写在 ESLint 的 `no-restricted-imports` 配置中（允许名单之外的导入报错），名单文件列入 `CODEOWNERS`。

## 6. TypeScript 写法

### 6.1 类型的严格程度

| 规则 | 检查 |
|---|---|
| 禁止 `any`；类型未知时用 `unknown` 再收窄 | `@typescript-eslint/no-explicit-any`、`no-unsafe-*` 系列（类型感知） |
| 禁止非空断言 `!` | `@typescript-eslint/no-non-null-assertion` |
| 类型断言 `as` 只在可信边界使用（框架的反序列化、测试数据构造）；禁止对对象字面量断言 | `@typescript-eslint/consistent-type-assertions`（`objectLiteralTypeAssertions: never`）；其余评审 |
| 禁止 `@ts-ignore`；`@ts-expect-error` 必须写理由 | `@typescript-eslint/ban-ts-comment`（D1） |

### 6.2 类型的来源

| 规则 | 说明 |
|---|---|
| 接口的请求与响应类型只来自 `generated/` | 不手写接口 DTO 的类型；需要页面专用的形状时，从生成类型派生（`Pick`、`Omit`） |
| 权限点、错误码、动作编码、字典类型使用生成的字面量类型 | 不把它们放宽成 `string`；比较错误时写 `error.code === ErrorCodes.Sample.NotOwner`（生成常量），不写字符串字面量 |
| 不可信来源的数据用 Zod 校验 | 导入文件、`sessionStorage`、`config.json`、跨浏览器标签页消息（F03 第 7.1 节）；接口响应不做运行时校验 |

### 6.3 类型声明的写法

| 规则 | 检查 |
|---|---|
| 对象的形状用 `interface`；联合、交叉、映射、工具类型用 `type` | `@typescript-eslint/consistent-type-definitions` |
| 不使用 `enum`、`namespace` | `erasableSyntaxOnly`（第 3.2 节）；取值集合用字面量联合或 `as const` 对象 |
| 只导入类型时写 `import type` | `verbatimModuleSyntax`、`@typescript-eslint/consistent-type-imports` |
| 函数的参数与返回值：导出的函数写明返回类型 | `@typescript-eslint/explicit-module-boundary-types`（只对 `platform` 开启；业务模块依赖推断） |

### 6.4 `null` 与 `undefined`

| 规则 | 说明 |
|---|---|
| 接口数据照生成类型 | 后端可空字段是 `null`（05-06），前端不在边界上悄悄转换成 `undefined` |
| 前端内部的“可选”用 `undefined` | 可选属性 `foo?: T`；不在同一个类型中混用两者表示同一件事 |
| 取默认值用 `??`，不用 `\|\|` | `\|\|` 会把 `0`、空字符串当成“没有值”（`@typescript-eslint/prefer-nullish-coalescing`） |

### 7.1 异步

| 规则 | 检查 |
|---|---|
| 每个 Promise 都要被等待、返回或明确交给框架处理 | `@typescript-eslint/no-floating-promises`、`no-misused-promises` |
| 用 `async` / `await`，不写 `.then` 链 | 评审 |

### 7.2 请求

| 规则 | 检查 |
|---|---|
| 业务模块不直接发请求：读经模块 `api.ts` + TanStack Query，写经 `useCommand`（F03 第 7.5、7.7 节） | 业务模块中使用 `fetch`、`XMLHttpRequest`、`openapi-fetch` 的 `createClient` 报错（`no-restricted-globals`、`no-restricted-imports`） |
| 不用 TanStack Query 的 `useMutation` | `no-restricted-imports`（F03 第 7.7 节：写入由 `useCommand` 负责幂等、版本、结果未知） |

| 按错误码判断，不比较错误文字 | `kmic/no-error-text-compare`：比较 `title`、`detail`、`message` 与字符串字面量即报错 |

### 7.3 状态放在哪里

| 状态 | 位置 | 检查 |
|---|---|---|
| 服务端数据 | TanStack Query 的缓存 | — |
| 页面的查询条件、表单、选择 | 页面组件或同目录的组合式函数（F03 第 6.1 节） | — |

| 浏览器存储 | 只经 `platform` 的封装（偏好走 `Ui.*`，F03 D5；结果未知清单，F03 第 7.5 节） | 业务模块中直接使用 `localStorage`、`sessionStorage`、`indexedDB` 报错 |

### 7.4 时间、日期与数值

| 规则 | 检查 |
|---|---|

## 8. 样式

### 8.1 D4 样式如何隔离

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A `<style scoped lang="scss">`** | Vue 为组件的元素加属性选择器，样式只作用于本组件；需要调整子组件内部时用 `:deep()` | Vue 的默认做法，模板中写普通类名，最易读；与组件库、VXE 的主题变量方式无冲突 | 样式会作用到子组件的根元素（Vue 已知行为）；`:deep()` 用多了会重新出现样式穿透 |
| B CSS Modules（`<style module>`） | 模板中写 `:class="$style.header"` | 完全隔离；类名可以有类型 | 模板变得冗长；覆盖组件库内部样式时仍要用 `:global`；生态中的示例与组件库文档都是 A 的写法 |
| C 不隔离，靠命名约定（BEM） | 全局样式 + 命名前缀 | 没有框架机制 | 隔离完全靠自觉；300 多个页面中必然冲突 |

- **决定（已确认，2026-11-05）**：A，并限制 `:deep()`：只允许在 `platform/ui`、`platform/table`（适配层调整组件库与 VXE 的内部样式）中使用，业务模块中使用即报错（Stylelint `selector-pseudo-class-disallowed-list`，按目录配置）。
- **理由**：可读性与生态一致性优先；隔离的薄弱点（`:deep()`）用目录限制控制住。
- **取舍**：子组件根元素会受父组件样式影响，页面写样式时以类名为准、不用元素选择器。

### 8.2 D5 样式用什么工具检查

F03 第 12 节规定“页面样式只能使用 `--kmic-*` 变量，禁止写死颜色值（F04 的检查规则）”，需要一个能检查 `.vue` 中 SCSS 的工具。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A Stylelint** | `stylelint` + `stylelint-config-standard-scss` + `stylelint-config-recommended-vue`（经 `postcss-html` 解析 `.vue`）+ `stylelint-declaration-strict-value`（指定属性只能用变量） | 样式检查的事实标准；能按属性要求“只能用变量”；与 ESLint 分工清楚 | 多一个工具和一份配置（均为 MIT，`待确认` 版本） |
| B 只靠评审 | — | 无工具 | 颜色值在评审中极易漏看；F03 已要求用工具检查 |
| C 自定义 ESLint 规则解析 `<style>` 块 | — | 只有一个工具 | 重新实现 Stylelint 已有的能力 |

- **决定（已确认，2026-11-05）**：A。
- **理由**：F03 已确定“用工具检查”，Stylelint 是唯一成熟的选择。
- **取舍**：多一个工具；确认后在 F02 第 11 节依赖总表中补充。

### 8.3 样式规则

| 规则 | 检查 |
|---|---|
| 颜色、字号、圆角、阴影、层级（`z-index`）、动效时长只能用 `var(--kmic-*)` | `scale-unlimited/declaration-strict-value`；`color-no-hex`、`color-named: never` |
| 间距优先用变量；布局尺寸（宽、高）可以写数值 | 间距由评审 |
| 禁止 `!important` | `declaration-no-important` |
| 业务模块不写全局样式（每个 `<style>` 都带 `scoped`） | `vue-scoped-css` 一类规则（`待确认` 选用的插件）或结构测试检查 `.vue` 文件 |
| `:deep()` 只在适配层使用 | D4 |
| 不用元素选择器、ID 选择器写页面样式 | `selector-max-id: 0`、`selector-max-type`（业务模块中为 0） |
| 断点只用框架提供的 SCSS 混入（F03 D11），不写数值 | 评审；混入之外的 `@media` 由 `at-rule-disallowed-list` 在业务模块中禁止 |
| 浅色 / 深色、密度无需页面处理 | 只用变量即自动适配（F03 第 12 节） |

## 9. 界面文字（F03 D10 交给本文的规则）

首期只有中文，业务页面的模板中直接写中文（F03 D10）。以下规则让以后启用多语言时能机械地完成抽取（前端延后事项“界面多语言”）：

| 规则 | 说明 | 检查 |
|---|---|---|
| 一句话在一处完整写出 | 一句话写在模板或一个模板字符串中；变化的只能是数量、名称这类**参数**，不能是句子片段。不同情况写成不同的完整句子。示例：写 `已提交 {{ count }} 条`，不写 `'已' + (isApprove ? '审批' : '提交') + count + '条'` | `kmic/no-text-concat`：含中文的字符串字面量参与 `+` 拼接、或模板字符串的插值是返回字符串的条件表达式，即报错 |
| 文字不埋在计算逻辑中 | 用户可见文字写在模板、或组件 `<script>` 中的常量与计算属性里；不在工具函数、store、请求函数中生成提示文字 | 评审 |

| 错误提示 | 使用 ProblemDetails 的 `title` / `detail`；前端只为 `Client.*` 本地错误写文字，集中在 `platform/texts`（F03 第 8 节） | 评审 |
| 框架文字集中 | 外壳、通用组件的文字在 `platform/texts`（F03 D10） | 评审 |
| 用词 | 自然、直接，不用营销式说法（FE-QA-08、06 附录 A.5）；业务名词与术语表的中文列一致；提示说清“发生了什么、用户可以做什么” | 评审 |
| 标点与空格 | 中文使用全角标点；中文与英文、数字之间加一个空格（与本项目文档一致） | 评审 |

## 11. 测试编写

### 11.1 D6 组件测试在什么环境中运行

F02 D10 已定 Vitest + Vue Test Utils、Playwright。还要决定组件测试的运行环境。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 纯逻辑在 Node 中测；组件在 Vitest 浏览器模式（Playwright 驱动 Chromium）中测；网络用 MSW 拦截** | 组合式函数、格式化、小数等不依赖界面的代码在 Node 中运行；组件挂载到真实浏览器中；请求在网络层由 MSW 返回，处理函数用生成的接口类型约束 | 布局、焦点、尺寸、虚拟滚动、弹层定位都是真实行为；目标浏览器只有 Chrome / Edge（F01），与测试一致；MSW 拦截真实请求，请求层（令牌、幂等键、错误转换）一并被测到 | 比 jsdom 慢；CI 需要 Chromium（端到端测试本来就需要）；多一个依赖（MSW，MIT） |
| B 组件在 jsdom / happy-dom 中测 | 模拟的 DOM | 快、成熟 | 没有真实布局：VXE 的固定列与虚拟滚动、弹层位置、`ResizeObserver` 等要大量模拟，测试通过不代表浏览器中正常；本系统最重要的组件（表格、表单、弹窗）恰好依赖布局 |
| C 组件不单独测，只靠端到端测试 | Playwright 覆盖页面 | 最接近真实 | 慢；失败时难以定位到组件；框架组件的边界情况无法逐一覆盖 |

- **决定（已确认，2026-11-05）**：A。
- **理由**：本系统的组件价值集中在表格、表单、弹窗等依赖真实布局与焦点的行为上，模拟 DOM 测不出它们的问题；目标浏览器单一，让组件测试直接在 Chromium 中运行成本可控。
- **取舍**：组件测试较慢（并行运行缓解）；多一个 MSW 依赖（确认后补入 F02 依赖总表）。Vitest 浏览器模式与 MSW 的配合已由前端原型 FP6 验证（`docs/frontend/spikes/FP-toolchain.md`）：需要把测试服务固定在 `127.0.0.1` 与固定端口（`test.api`），并在测试配置中 `resolve.dedupe: ['vue']`。

### 11.2 D7 测试描述用什么语言

后端 06 D9 定测试方法名用英文，原因是方法名是标识符（D3 只允许英文）。前端的测试描述是 `describe` / `it` 的**字符串参数**，不是标识符。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 英文（与后端同形） | `it('keeps the idempotency key when retrying')` | 与后端一致 | 前端测试断言的是用户看到的中文界面，用例描述与用例内容两种语言 |
| **B 中文描述，标识符仍为英文** | `it('结果未知后重试使用原幂等键')`；变量、函数照 D3 用英文 | 前端测试描述的是用户可见的行为，测试体中的定位（`getByRole('button', { name: '提交' })`）本来就是中文；描述与注释同属“给人读的文字”（06 D7 规定中文）；业务名词用术语表的中文列，“一个概念一个名字”仍然成立 | 前后端测试报告的语言不同 |

- **决定（已确认，2026-11-05）**：B。
- **理由**：后端选英文是因为方法名受标识符规则约束；前端描述不受这个约束，按 06 D7“给人读的文字用中文”处理更一致。
- **取舍**：前后端测试报告的语言不同。

### 11.3 其他测试写法

| 规则 | 说明 | 检查 |
|---|---|---|
| 结构 | 准备 / 执行 / 断言三段，用空行分隔 | 评审 |
| 一个测试只验证一个行为 | 可以有多个断言，但都服务于同一个行为 | 评审 |
| 元素定位 | 按角色、标签文字、可见文字定位（`getByRole`、`getByLabel`）；没有可访问的方式时才用 `data-testid`，并把这视为可访问性缺陷的信号 | 评审 |
| 不用固定时长等待 | 禁止 `waitForTimeout`、`setTimeout` 等待；时间相关的逻辑用假时钟（`vi.useFakeTimers`、`platform/time` 的替换） | `playwright/no-wait-for-timeout`；Vitest 中由评审 |
| 不用组件的 DOM 快照 | 快照测试脆弱且无法说明意图；只断言行为 | 评审 |
| 测试数据 | 用以生成类型约束的构造函数（`sampleRow({ status: 'submitted' })`）；不用随机数据（失败不可重现，与 06 第 12.3 节相同） | 评审 |
| 跳过测试 | `it.skip` / `test.skip` 必须带跟踪编号 | `kmic/todo-with-issue` 同一规则 |
| 端到端测试 | 连接真实后端与参考模块 `Sample`（F03 第 17 节）；权限矩阵与后端 05-05 第 12.2 节共用同一份数据；可访问性用 axe-core 检查 | — |
