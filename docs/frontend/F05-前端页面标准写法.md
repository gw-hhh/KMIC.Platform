| 规则 | 说明 |
|---|---|
| 与后端模块一一对应 | 目录名为后端模块名的小写短横线形式；接口路径的模块前缀相同（`/api/v1/sample`） |
| `pages/` 中只放页面组件 | 每个页面组件都必须被路由目录引用（F04 第 14.4 节结构测试） |
| 模块很大时 | `api.ts` 按资源拆为 `api/` 目录；`pages/`、`components/` 按资源分子目录 |

### 2.2 D1 模块如何登记到应用

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 显式登记表** | `app/modules.ts` 列出全部模块：`export const modules = [sampleModule, customerModule]`；每个模块的 `index.ts` 导出名字与路由 | 应用包含哪些模块一目了然；与后端宿主中的 `AddModule<…>()`、模块登记表（07 第 2.4 节）一致；参考模块按环境登记（D2）写在同一处 | 新增模块多一行登记 |
| B 自动发现 | `import.meta.glob('../modules/*/index.ts')` 扫描目录 | 不需要登记 | 应用包含什么由目录结构隐式决定；按环境排除某个模块要另写规则；删除目录前留下的半成品模块会被意外带入 |

- **决定（已确认，2026-11-05）**：A。
- **理由**：模块是系统的一级结构，显式登记让“有哪些模块”成为可评审的一处代码；多出的一行登记换来与后端一致的可见性。
- **取舍**：新增模块多一个步骤（第 15 节）。

### 2.3 D2 参考模块 `Sample` 在生产中如何处理

后端 07 D3：参考模块 `Sample` 常驻仓库、随 CI 编译测试，生产环境不注册。前端对应的 `modules/sample` 同样是写法样板与端到端测试的对象。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 同一构建；按运行时配置决定是否登记路由** | `app/modules.ts` 中 `{ module: sampleModule, onlyIn: 'nonProduction' }`；应用启动时读取 `config.json` 的环境名（F03 D8），生产环境不登记 `Sample` 的路由与菜单 | 同一镜像从测试晋级到生产（ADR-0032 D5、F03 D8）；`Sample` 的页面按需加载，生产中从不下载 | 生产构建产物中仍包含 `Sample` 的代码分块（不会被加载） |
| B 构建时排除 | 生产单独构建，不包含 `Sample` | 产物中完全没有 | 违反“一次构建、多环境部署”：测试环境验证过的不是生产运行的产物 |
| C 单独的样板应用 | 另建一个只用于演示与测试的应用 | 完全隔离 | 要复制一份外壳与装配；样板与真实应用的装配可能不一致，失去“样板即真实写法”的意义 |

- **决定（已确认，2026-11-05）**：A；结构测试断言：以生产配置装配的路由目录中不含 `sample.*`。
- **理由**：与后端“生产不注册”同一语义，同时满足前端已定的“一次构建”。
- **取舍**：生产产物中多一个不会被加载的代码分块。

## 3. 一个页面的组成

| 规则 | 说明 |
|---|---|
| 路由参数经属性传入 | 路由条目声明参数，页面用 `defineProps<{ id: string }>()` 接收；页面中不调用 `useRoute()`（类型明确、测试时直接传属性） |
| 页面组件只做装配 | 查询、命令、表单、表格的组合；超过约 300 行时提取同目录的组合式函数或子组件（F04 第 5.2 节） |
| 页面与外壳的交互只经 `usePage()` | 标题、未保存、关闭、打开弹窗（F03 第 6.1 节） |
| 页面之间的跳转只经 `navigate(路由名, 参数)` | 类型化导航（F03 第 4.1 节）；不拼接路径 |
| 页面之间不传数据对象 | 只传 ID；目标页面自己加载（数据可能已变化，且标签可能被单独刷新） |

## 4. `api.ts`：查询与命令的定义

```ts
// modules/sample/api.ts（示例；defineModuleApi 的确切签名以框架实现为准）
import { defineModuleApi } from '@/platform/api';

export const sampleApi = defineModuleApi('sample', ({ query, command }) => ({
  list: query('GET', '/api/v1/sample/samples'),            // 参数与响应类型由生成的 paths 推断
  detail: query('GET', '/api/v1/sample/samples/{id}'),
  history: query('GET', '/api/v1/sample/samples/{id}/history'),
  create: command('POST', '/api/v1/sample/samples'),        // 是否带幂等键由 OpenAPI 的 x-idempotent 决定（F03 第 7.5 节）
  update: command('PUT', '/api/v1/sample/samples/{id}'),
  submit: command('POST', '/api/v1/sample/samples/{id}/submit'),
  remove: command('DELETE', '/api/v1/sample/samples/{id}'),
  startExport: command('POST', '/api/v1/sample/samples/exports'),
}));
```

| 用途 | 写法 |
|---|---|
| 读取 | `useQuery(() => sampleApi.detail.options({ path: { id } }))`：返回 TanStack Query 的选项，查询键为 `[纪元, 'sample', …路径与参数]`（F03 第 7.7 节） |
| 写入 | `useCommand(sampleApi.submit, { invalidates: [sampleApi.detail.key({ path: { id } }), sampleApi.list.all] })` |
| 失效 | `sampleApi.list.all` 表示该查询的全部参数组合；`key(...)` 表示一组具体参数 |

| 规则 | 说明 |
|---|---|
| 一个模块一个 `api.ts` | 页面不直接调用请求客户端，也不手写查询键（F04 第 7.2 节） |
| 路径只来自生成的 `paths` | 写错路径即类型检查失败 |
| 只有 `GET` 定义为查询 | 其余方法一律定义为命令，经 `useCommand` 执行 |
| 不访问其他模块的接口 | 需要其他模块的数据时，用其他模块的引用选择接口（第 8.2 节）或跳转到其页面；与后端“模块之间只经 Contracts”对应 |

## 5. 列表页

```vue
<!-- modules/sample/pages/SampleListPage.vue（示例） -->
<script setup lang="ts">
import { Button } from 'antdv-next';
import { KListPage, KQueryForm, KFormItem, KInput, KEnumSelect, KDateRange } from '@/platform/ui';
import { KTable, defineColumns } from '@/platform/table';
import { useListQuery } from '@/platform/api';
import { useCan } from '@/platform/authz';
import { navigate } from '@/platform/page';
import { Permissions } from '@/generated/permissions';
import type { SampleListItem } from '@/generated/types';
import { sampleApi } from '../api';

const list = useListQuery(sampleApi.list, {
  defaults: { q: '', status: [], createdFrom: undefined, createdTo: undefined },
  pageSize: 20,
});

const columns = defineColumns<SampleListItem>([
  { id: 'number', title: '单号', width: 140, fixed: 'left', link: (row) => ['sample.detail', { id: row.id }] },
  { id: 'title', title: '标题', minWidth: 200 },
  { id: 'status', title: '状态', width: 100, format: { enum: 'SampleStatus' } },
  { id: 'createdAt', title: '创建时间', width: 160, format: 'dateTime', sortable: true },

const canCreate = useCan(Permissions.Sample.Create);
</script>

<template>
  <KListPage>
    <template #query>
      <KQueryForm :list="list">
        <KFormItem label="关键字" field="q"><KInput v-model="list.draft.q" /></KFormItem>
        <KFormItem label="状态" field="status">
          <KEnumSelect v-model="list.draft.status" enum="SampleStatus" multiple />
        </KFormItem>
        <KFormItem label="创建日期" field="createdFrom">
          <KDateRange v-model:from="list.draft.createdFrom" v-model:to="list.draft.createdTo" />
        </KFormItem>
      </KQueryForm>
    </template>
    <template #toolbar>
      <Button v-if="canCreate" type="primary" @click="navigate('sample.create')">新建</Button>

    <KTable table-key="sample.list.samples" :columns="columns" :list="list" />
  </KListPage>

```

| 规则 | 说明 |
|---|---|
| 布局固定 | `KListPage`：查询区 → 操作区 → 表格 → 分页（F03 第 9.2 节） |
| 查询状态 | `useListQuery`：草稿与已提交分离（点“查询”才生效），页码、页大小、排序随之管理；查询条件的类型来自生成的查询参数类型，字段名与后端筛选模型一致（05-06 第 6.4 节） |
| 日期筛选 | 日期参数是 `YYYY-MM-DD`（后端为 `DateOnly`，07 第 4.4 节）；时刻范围由框架按业务时区换算（F03 第 9.3 节） |
| 列定义 | 稳定列 ID（偏好按 ID 保存）；格式化只用框架提供的类型（日期、时刻、金额、字典、枚举，F04 第 9 节）；可排序的列必须在 `x-sortable-fields` 中（类型检查） |
| 表格键 | `模块.页面.表格`，用于保存列设置（F03 D5） |
| 进入详情 | 单号列的链接或行双击，`tab.mode = byParams` 保证同一单据只开一个标签 |
| 行操作 | 列表不返回 `allowedActions`（05-05 D10）：行操作按权限点决定是否显示，点击后由接口判断，拒绝时按 F03 第 8 节提示 |
| 合计与总数 | 合计来自接口；`totalCountExact = false` 时由 `KTable` 显示“10,000+”（F03 第 9.2 节） |

**补充说明（2026-11-05，随 F07 确认）**：操作区并入表格卡片的顶部栏（F07 D5）：页面按钮写在 `KTable` 的 `#toolbar` 插槽中，与表格工具同一行；列表页的写法以 F07 第 3.2 节为准（`defineColumns(接口, 列)` 从接口推断行类型与可排序字段，行操作用 `defineRowActions`，只按权限点显示，F07 D7）。合计行首版不提供（前端延后事项“合计行”）。

## 6. 详情页

```vue
<!-- modules/sample/pages/SampleDetailPage.vue（示例） -->
<script setup lang="ts">
import { Descriptions, DescriptionsItem } from 'antdv-next';
import { KDetailPage, KActionButton, KDateTime, KEnumText, KStateHistory } from '@/platform/ui';
import { useCommand } from '@/platform/api';
import { usePage, navigate } from '@/platform/page';
import { useConfirm } from '@/platform/ui/feedback';
import type { SampleDetailResponse } from '@/generated/types';
import { sampleApi } from '../api';
import SampleItemsTable from '../components/SampleItemsTable.vue';

const { id } = defineProps<{ id: string }>();
const page = usePage();
const detail = page.useQuery(() => sampleApi.detail.options({ path: { id } }));
page.useTitle(() => (detail.data.value ? `示例 ${detail.data.value.number}` : undefined));

const confirm = useConfirm();
const submit = useCommand(sampleApi.submit, {
  invalidates: [sampleApi.detail.key({ path: { id } }), sampleApi.list.all],
});

async function onSubmit(data: SampleDetailResponse) {
  if (!(await confirm('提交后不能再修改，确定提交吗？'))) return;
  await submit.run({ path: { id }, body: { expectedVersion: data.version, reason: null } });
}
</script>

<template>
  <KDetailPage :query="detail">
    <template #actions="{ data }">
      <KActionButton :actions="data.allowedActions" action="edit" @click="navigate('sample.edit', { id })">
        编辑
      </KActionButton>
      <KActionButton :actions="data.allowedActions" action="submit" :command="submit" @click="onSubmit(data)">
        提交
      </KActionButton>
    </template>
    <template #default="{ data }">
      <Descriptions :column="3">
        <DescriptionsItem label="单号">{{ data.number }}</DescriptionsItem>
        <DescriptionsItem label="状态"><KEnumText :value="data.status" enum="SampleStatus" /></DescriptionsItem>
        <DescriptionsItem label="创建时间"><KDateTime :value="data.createdAt" /></DescriptionsItem>
      </Descriptions>
      <SampleItemsTable :items="data.items" readonly />
      <KStateHistory :query="sampleApi.history.options({ path: { id } })" />
    </template>
  </KDetailPage>
</template>
```

| 规则 | 说明 |
|---|---|
| 加载、不存在、出错 | 由 `KDetailPage` 统一显示：404 显示“数据不存在或无权查看”（F03 第 8 节），页面不另写 |
| 动作按钮只依据 `allowedActions` | `KActionButton` 按动作编码判断显示；不在前端组合“权限点 + 状态”（F03 第 4.4 节）；动作编码来自生成的字面量类型 |
| 动作命令带版本 | 请求体带 `expectedVersion = data.version`；409 版本冲突按 F03 第 7.5 节处理 |
| 有破坏性的动作先确认 | 用 `platform/ui` 的确认函数（F04 第 5.8 节）；确认文字是完整的一句话（F04 第 9 节） |
| 动作成功后 | 由 `invalidates` 失效详情与列表；当前标签立即重新加载，其他标签在激活时重新加载（F03 第 7.7 节） |
| 流转记录 | 模块提供历史查询（05-09：先按正常授权加载资源，再取历史），页面用 `KStateHistory` 显示 |
| 标题 | 加载后改为“对象名 + 单号”，便于在标签栏中区分 |

## 7. 新建与编辑

### 7.1 D3 新建与编辑用标签页还是抽屉

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| A 一律用标签页 | 新建、编辑都是独立路由与页面实例 | 一种写法；有地址、可刷新恢复标签；空间充足 | 只有两三个字段的简单对象也要开一个标签，打断列表上的操作 |
| **B 按规则选择：标签页为默认，简单对象用抽屉** | 有明细行、附件、字段较多（约 10 个以上），或需要与其他页面对照 → 标签页；只有少量字段、无明细与附件的简单对象 → 从列表打开的抽屉（`page.openDialog`），属于列表的页面实例 | 复杂对象有完整空间与独立生命周期；简单对象不离开列表 | 两种写法；规则的边界要在模块设计中逐个判断 |
| C 一律用弹窗或抽屉 | 与旧系统弹出层习惯相近 | 不离开列表 | 复杂单据在弹窗中空间不足；弹窗没有地址，刷新即丢失；嵌套弹窗难以管理 |

- **决定（已确认，2026-11-05）**：B；模块设计文档的页面清单中写明每个对象用哪一种（第 17 节）。
- **理由**：复杂单据需要独立的页面实例来承载未保存、保存中、结果未知的完整生命周期（F03 第 6.2 节）；简单对象在抽屉中编辑，同样有未保存保护（F03 第 11.5 节），且不打断列表操作。
- **取舍**：两种写法并存，由规则约束选择。

### 7.2 D4 详情与编辑是否分开

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 分开：详情页只读 + 动作，编辑是另一个路由** | `sample.detail`（只读、动作按钮）与 `sample.edit`（表单，`tab.mode = byParams`，参数 `id`）；表单组件 `SampleForm` 由新建页与编辑页共用 | 每个页面实例只有一种生命周期：详情页没有未保存状态，编辑页的未保存、保存中、结果未知与离开保护一一对应（F03 第 6.2 节）；新建与编辑共用同一个页面形态；与后端“查询 / 命令”分离对应 | 编辑时同一单据有两个标签（保存后编辑标签自动关闭） |
| B 同一页面内切换只读与编辑 | 详情页上点“编辑”切换为表单 | 标签少；编辑时仍能看到状态与流转记录 | 一个页面实例时而有表单、时而没有，离开保护与状态管理变复杂；详情页组件同时承担展示与编辑，体量大 |
| C 详情页本身就是表单 | 打开即可编辑 | 操作最少 | 只读状态（已提交）与可编辑状态混在同一个表单中，误改风险高；与 `allowedActions` 的“编辑”动作不对应 |

- **决定（已确认，2026-11-05）**：A。
- **理由**：页面实例的生命周期是本系统前端的核心机制，A 让它与页面一一对应；表单组件复用让新建与编辑只有一份字段与校验。
- **取舍**：编辑期间同一单据有两个标签。

## 13. D5 智能枚举的显示名与上传档案如何到前端

写本文时发现两处契约缺口：

- **智能枚举的显示名**：05-06 把智能枚举输出为 `type: string, enum: [全部 Code]`，前端只得到编码（`Submitted`），没有显示名（“已提交”，05-01 第 6 节的 `Name`）。列表的状态列、状态筛选都需要显示名。
- **上传档案**：F03 第 11.6 节要求前端“按上传档案预先检查类型与大小”，但档案的大小上限与允许类型没有导出给前端。

| 选项 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A 写入 OpenAPI 文档的扩展字段，前端生成** | 文档级扩展 `x-kmic-enums`（智能枚举名 → `[{ code, name }]`）、`x-kmic-upload-profiles`（档案名 → 显示名、大小上限、允许类型）；前端生成脚本产出 `generated/enum-labels.ts`、`generated/upload-profiles.ts` | 与 05-06 第 7.2 节已确认的做法（权限点、错误码、字典类型都经文档扩展导出）完全一致；编译期可用、有类型；这两类元数据都在代码中声明，随版本发布，不需要运行时接口 | 显示名修改需要重新生成并发布前端（前后端同仓库、同一流水线，影响小） |
| B 运行时接口 | 前端启动时请求枚举与档案的元数据 | 后端改名即生效 | 启动多一个请求；失去编译期类型；这些元数据本来就只随代码变化 |
| C 接口响应中带显示名，前端自己维护档案 | 每个 DTO 加 `statusName`；档案在前端重复声明 | 不需要生成 | DTO 中到处是冗余字段，且与“接口只返回编码、前端翻译”的字典做法不一致（05-10 D4）；档案两处声明必然不一致 |

- **决定（已确认，2026-11-05）**：A。已给 05-06 第 7.2 节加补充说明（两个文档级扩展的内容与检查），给 F03 第 11.1、11.6 节加补充说明（`KEnumSelect`、`KEnumText`、表格的枚举格式从 `enum-labels.ts` 取显示名；`KUpload` 从 `upload-profiles.ts` 取档案）。
- **理由**：沿用已确认的同一机制补上缺口，不引入新的通道。
- **取舍**：显示名的修改随版本发布。

| 细则 | 说明 |
|---|---|
| 枚举的键 | 智能枚举在 OpenAPI 文档中的架构名，即前端生成的类型名（如 `SampleStatus`）；页面写 `enum="SampleStatus"` 时类型检查只接受已生成的键 |
| 顺序 | 选项按后端声明顺序排列，前端不另行排序 |
| 未知编码 | 前端版本落后于后端时可能遇到未生成的编码：原样显示编码，不报错（与字典的未知编码一致，F03 第 11.1 节） |
| 与延后事项“界面多语言”的关系 | 生成的显示名只有中文。触发多语言时，`enum-labels.ts` 作为 `zh-CN` 的来源，键为 `枚举名.编码`，其他语言在模块的 `locales/` 中按同一键补充；本决定的做法不需要改（已写入前端 00-README 延后事项表） |
