# Codex 整理的注释讨论与规则

用户认为部分注释有明显的 AI 味，读着别扭、含义不清，并进一步提出注释数量可能偏多。目标是让必要的注释准确、自然、容易理解，同时减少重复和干扰。

以下内容来自这次讨论，供后续确认和执行。Codex 尚未把它们写入项目的正式规则文件。

## 用户关注的问题

用户原话包括。

> 注释，是不是有点太乱了，一股AI味的注释，根本不通俗易懂读者不通顺。怎么解决有什么skill之类的好方法吗。

> 为什么我的规范里面明明有些代码规范注释规范，为什么claude code前面写的还行，后面为什么注释都是这样的，没有参考我想要的来。

> 然后就是，目前的注释是不是有点太多了。

Codex 抽查了 Sample、Files 和部分框架、Operations 代码，并读取了 `CLAUDE.md`、`docs/framework/06-coding-standards.md` 及检查脚本中的相关规则。

## 抽查发现

| 问题 | 实际例子 | 阅读影响 |
|---|---|---|
| 关系不清 | 负责人，创建者 | 无法直接判断两者是相同概念、默认关系还是并列含义 |
| 句子堆叠 | 一句里同时交代更新消息、最终一致性和清理规则 | 需要读者自行拆解逻辑 |
| 口语过于随意 | 被移除的那个、能不能增删附件 | 指代含糊，公共说明不够准确 |
| 表达压缩 | 状态的起点同时写入业务历史 | 句子短，但理解费劲 |
| 描述与实现有偏差 | 一次最多 50 个 | 实际数量上限来自配置，50 是默认值 |
| 重复说明 | 实现方法再次写接口已有的用途和参数 | 增加阅读量和维护负担 |
| 类头说明过重 | 长段介绍设计背景和完整执行流程 | 阅读具体代码前先被大量说明打断 |

这些发现来自抽查，尚未覆盖全项目。已有的“标题”“状态”“附件”等短注释，部分用于接口文档或数据库列说明，保留与否需要检查用途。

## 为什么有规范仍会写偏

项目已有“自然、简短”“不堆设计说明”“接口实现用继承文档”等要求，也有注释格式和用词检查。Codex 判断，当前实际输出与这些要求之间仍有差距。

下面是可能原因，不能作为 Claude Code 当时运行过程的已确认事实。

- “自然、通俗”可能被理解为随意口语，“简短”可能被理解为压缩句子。
- 用途、约束、参数和返回结果需要分别安排，实际生成时可能全塞进一句话。
- 前面生成的别扭写法可能被后续代码继续模仿。
- 格式和禁用词检查可以通过，语义不清和句子不顺仍然可能存在。

是否受长会话、上下文压缩或规则漏读影响，需要查看 Claude Code 当时的会话记录。仅凭代码无法确定。

## 注释的取舍

| 情况 | 处理建议 |
|---|---|
| 简单内部成员，名称已表达含义 | 通常不写注释 |
| 普通赋值、取值、查询、循环和判断 | 删除逐句复述代码的说明 |
| 公共接口和影响正确调用的约定 | 保留必要说明 |
| 接口文档字段、数据库列说明 | 保留准确、简短的含义 |
| 关键业务规则、权限、事务、并发、资源释放 | 保留影响正确使用和安全修改的信息 |
| 接口实现重复接口说明 | 优先使用 `<inheritdoc />` |
| 类头堆叠实现流程或开发过程 | 精简，必要的局部原因放到相关代码旁 |
| 已经准确清楚的注释 | 保留，避免单纯换一种说法 |

## 讨论形成的注释规则

注释质量以准确、清楚、读起来顺畅为标准，数量保持克制。读者应能结合当前代码理解注释，无需回看开发对话或依赖作者解释。

### 内容

- 优先通过清晰的命名和代码结构表达含义。简单内部成员、普通赋值、查询和判断通常不写注释。
- 公共接口、接口文档字段及数据库列说明所需的注释，简短写清用途或含义。
- 关键业务规则、调用前提、权限责任、事务顺序、并发约束和失败处理，保留必要说明。
- 看起来多余、实际必须保留的特殊处理，写清原因。
- 已经准确清楚的注释保留，多余或重复的说明删除。

### 表达

- 使用自然、准确的书面中文，像同事认真解释代码。避免汇报腔、术语堆叠和随意口语。
- 写清楚谁做什么、什么条件下发生什么。多个对象同时出现时，明确指代。
- 一句话表达一个主要意思。简短说明可以用名词短语，涉及业务关系和调用约定时，把意思表达完整。
- 用途、参数含义、返回结果和设计原因放在合适的位置。局部约束写在相关代码旁。
- 必要的专业术语照常使用，结合当前代码说明含义。
- 业务关系、执行顺序和处理约定必须有实现或设计依据。原意不明确时，先核实再改写。

### 数量

- 不逐句翻译代码，不机械补齐注释模板。
- 不在类头罗列整套实现流程，不在多处重复同一份说明。
- 接口上写完整约定，实现成员优先使用 `<inheritdoc />`。
- 简单内部成员按需要写。实体、配置类等属性是否必须注释，按接口文档、数据库说明等实际用途确定。
- 精简时保留影响正确使用和安全修改的约束。

### 修改后检查

1. 表达是否通顺，主语和指代是否明确？
2. 是否存在歧义、术语堆叠或一句话塞入多个意思？
3. 是否只是重复代码，或者在其他位置已经说明？
4. 业务含义是否与实现、调用方和设计一致？
5. 精简后是否丢失了必要的调用约定？

## 与现有项目规则的关系

整理时，项目规范还要求实体和配置类的公开属性写 XML 注释，部分公开框架成员缺少注释会导致构建失败。正式减少这类注释前，应先检查接口文档、数据库说明和构建约束的用途。

注释整理限于表达和必要说明。业务文案、条件判断、异常行为及执行顺序的调整，需要按各自的任务范围处理。

## 关于 skill 的讨论

Codex 建议先选少量典型文件，由用户确认改写风格，再把认可的正反例和审查步骤整理成项目专用的 C# 注释审查 skill。

| 做法 | 适合承担的作用 | 局限 |
|---|---|---|
| 项目规则 | 日常开发的基本要求 | “自然、简洁”仍有理解空间 |
| 专用 skill | 固定阅读实现、核实含义、改写、复查的流程，并附真实例子 | 需要通过输出结果校准，不能保证每次表达都合格 |
| 自动检查 | 格式、明显套话、重复的机械问题 | 难以准确判断句子通顺程度和业务含义 |

后续可以使用 `skill-creator` 创建 skill。当前只是讨论了这个做法，尚未创建或安装。

关于 skill 的官方说明见 [OpenAI 的技能创建与评估说明](https://developers.openai.com/blog/eval-skills)。
